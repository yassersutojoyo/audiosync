# Windows silent output: installing VB-CABLE from the double-audio notice

Behavior spec for the Windows app (`desktop/`). It covers one change: on a PC with no virtual output, the double-audio notice offers one button that installs VB-CABLE, the vendor's free virtual audio cable, unmodified and fetched from the vendor at that moment. Once the cable exists, the code that already moves the sound to a silent virtual output takes over, so the source is heard once.

Each clause has an ID (`VC` and a number) and its sources. Section 1 is what was found about the package (team A facts); sections 2 to 4 are what the app does, how it is tested and what the public text says. File and line references are to `main` on 2026-11-20. Vendor pages were read on 2026-11-20 unless a clause says otherwise.

Why it is needed: without a virtual output, the PC's own output plays the source ahead of the synced speakers and the notice asks the user to fix the routing by hand ([WINDOWS_AUDIO_ROUTING.md](WINDOWS_AUDIO_ROUTING.md), first section). The decisions this spec builds on: the package is fetched from the vendor at click time and checked against a pinned SHA-256, nothing of it ships in AudioSync's release files, only the free VB-CABLE is used (not A+B or C+D), the click shows the product's name, that it is donationware and the vendor's link, nothing is installed without the click, the user installs in the vendor's own setup window, and AudioSync writes no driver of its own.

## 1. The package (facts)

- **VC1** Download. The vendor's page lists `VBCABLE_Driver_Pack46.zip` at `https://download.vb-audio.com/Download_CABLE/VBCABLE_Driver_Pack46.zip`, 1.29 MB, "XP to WIN11 32/64 bits/Arm64". The server returned it directly (HTTP 200, no redirect) with `Last-Modified: Sat, 31 Oct 2026 10:17:59 GMT` and `Content-Length: 1324680`. Sources: [vb-audio.com/Cable](https://vb-audio.com/Cable/); a download on 2026-11-20.
- **VC2** Pinning. The file name carries the pack number, and the vendor still serves the 2015 `VBCABLE_Driver_Pack43.zip` next to it, so a pack's URL stays up after a newer one appears. Its SHA-256 on 2026-11-20 was `bc44e8974191a5a2427d6c979e2dab08dbb09925f3f435dfa2f0ba3e45b6eb90`, the same value the Windows calibrate-loop job pinned on 2026-11-18 (commit 9027db37e, `scripts/stranger/windows_calibrate.ps1`, not on `main`). Nothing on the vendor's pages promises that a pack is never replaced under the same name; the pin turns such a replacement into a hash mismatch (VC33), not into running a file nobody checked. Sources: [vb-audio.com/Cable](https://vb-audio.com/Cable/); the two downloads.
- **VC3** Contents. The zip holds 31 files: the 64-bit Windows 10 and later package (`vbMmeCable64_win10.inf`, `vbaudio_cable64_win10.cat`, `vbaudio_cable64_win10.sys` for x64, `vbaudio_cable64arm_win10.sys` for ARM64), older drivers for XP to Windows 7, `VBCABLE_ControlPanel.exe`, `readme.txt`, two icons, and two setup programs: `VBCABLE_Setup_x64.exe` (x86-64) for 64-bit Windows and `VBCABLE_Setup.exe` (x86) for 32-bit Windows, which "will do nothing on 64 bit O/S". There is no ARM64 setup program. The setup cannot run from inside the zip; every file has to be extracted first. Sources: `unzip -l` and the PE headers of the 2026-11-20 download; `readme.txt` in the zip; the setup's own message "Installation cannot work from a ZIP folder"; [Reference Manual](https://vb-audio.com/Cable/VBCABLE_ReferenceManual.pdf), October 2024, revision 3, page 4.
- **VC4** Signatures. `VBCABLE_Setup_x64.exe` carries a valid Authenticode signature by "BUREL VINCENT Entrepreneur individuel" (GlobalSign EV code signing), so the UAC prompt names that publisher, not AudioSync. The Windows 10 driver catalog is signed by "Microsoft Windows Hardware Compatibility Publisher". Source: `Get-AuthenticodeSignature` on the extracted files, 2026-11-20.
- **VC5** Silent switches, not used in the shipped path. `VBCABLE_Setup_x64.exe -i -h` installs without the setup's own windows. This is not in the vendor's documentation; it comes from users on the vendor's forum, uncontradicted by the site admin ([2023](https://forum.vb-audio.com/viewtopic.php?p=6681), [2024](https://forum.vb-audio.com/viewtopic.php?p=7129)). The app runs the setup with no switches (VC33), so the user sees the vendor's own window and presses its install button; only the runner's unattended leg installs without that window (VC52). The same posts report that the Windows Security dialog that asks whether to install the device software still appeared, and the admin answered that it is a system dialog the setup cannot suppress. Microsoft documents that a driver package signed by a Windows signing authority (WHQL) installs without that dialog, and only a package from a publisher not yet trusted shows it to an administrator ([Signature categories and driver installation](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/signature-categories-and-driver-installation), [PnP device installation signing requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/pnp-device-installation-signing-requirements--windows-vista-and-later-)). Pack46's catalog is Microsoft-signed (VC4), so one UAC prompt and no second dialog is expected, but it is unproven until VC52 passes. The setup's exit code meaning is not documented anywhere found.
- **VC6** Restart. The vendor says to reboot after installing and after removing ([vb-audio.com/Cable](https://vb-audio.com/Cable/); Reference Manual page 4; `readme.txt`), and the setup has the messages "But you might REBOOT to finalize it." and "But you must RESTART your system". On a hosted runner (image windows-2025-vs2026), the same package installed through `pnputil` and `devcon` gave active endpoints within the job's 60-second wait, with no restart (CI run 44392683543, 2026-11-18, `env.txt` artifact). Whether the setup program's path also works without a restart is what VC51 measures.
- **VC7** ARM64. The vendor lists ARM64 support for Windows 10 and 11, and the manual says the setup picks the right driver for the running system. The INF has an `NTARM64.10.0...16299` section that installs `vbaudio_cable64arm_win10.sys`. The only 64-bit setup is an x86-64 program, so on ARM64 it runs under Windows 11's x64 emulation ([Windows on Arm](https://learn.microsoft.com/en-us/windows/arm/overview)). No ARM64 install has been observed. Sources: [vb-audio.com/Cable](https://vb-audio.com/Cable/); Reference Manual page 4; the INF in the zip.
- **VC8** Default devices. The vendor's manual: "With Windows 10 and higher, the last installed audio driver can be automatically set as default device", in which case all PC sound goes into the cable and the default microphone becomes the cable's output. So an install can move both the default playback and the default recording device. The runner in VC6 had no other device, so it says nothing either way. Source: Reference Manual page 6, "Set VB-Cable as default device".
- **VC9** Device names. The package adds one device, "VB-Audio Virtual Cable" (hardware ID `VBAudioVACWDM`, manufacturer "VB-Audio Software", under the `ROOT` enumerator), with three endpoints: playback "CABLE Input" (two channels), playback "CABLE In 16 Ch", and recording "CABLE Output". Windows shows the device name in parentheses after each, as in "CABLE Input (VB-Audio Virtual Cable)". The endpoint name is not reliable: on the windows-2025 runner the two-channel playback endpoint was named "Speakers (VB-Audio Virtual Cable)". Sources: `[Strings]` of `vbMmeCable64_win10.inf`; CI run 44392683543 `env.txt`; commit c7cf5b9ec.
- **VC10** Removal. Running the setup again when the cable is present offers Remove Driver instead of installing; a restart finishes the removal, and Device Manager is the fallback. The setup also writes an entry under the system's Uninstall registry key, so it can be expected under Settings > Apps > Installed apps; the entry's name and the program it runs are confirmed by VC53. Sources: Reference Manual page 5, "Uninstall VB-Cable"; the setup's strings `Remove Driver`, `UninstallString` and `SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall`.
- **VC11** Licence. The licensing page (read 2026-11-18 and again 2026-11-20) allows "the distribution of the VB-CABLE package AS IS together with your application" and embedding it "through a silent installation process", "provided that our donationware model remains applicable": the end user can identify VB-CABLE as a VB-Audio product, and the application mentions at least "The origin of VB-CABLE : www.vb-cable.com." and "VB-CABLE is a donationware, all participations are welcome." In a professional environment the distributor must buy licences; A+B and C+D cannot be bundled. `www.vb-cable.com` redirects to `https://vb-audio.com/Cable/index.htm`. The older `readme.txt` in the zip (dated 2024-10-08) still says the package may not be integrated in another installation procedure without the author's agreement; the licensing page is the newer statement. Sources: [licensing page](https://vb-audio.com/Services/licensing.htm); `readme.txt`.

## 2. Behavior

### Today's code it builds on

- **VC20** The silent output. `silent_endpoint` takes only an output of kind Virtual that the user hasn't turned on, one nobody listens to first (`desktop/src/audio/default_output.rs:92-102`). An output is Virtual when its device's enumerator is `ROOT` (`desktop/src/audio/outputs.rs:143-157`), which VB-CABLE's is (VC9), so its two playback endpoints qualify with no change. The default output is moved for All System Audio, and one app's output for a single app (`desktop/src/audio/controller.rs:1432-1438`). The notice is raised only when nothing can take the source off the outputs the user hears (`controller.rs:4730-4741`, S382), and its text is in `desktop/ui/strings.slint:994-1010` (system) and `973-989` (app), with the Show How button at `strings.slint:84-86`.

### Offer

- **VC21** When the button shows. The double-audio notice carries the install button only when all of these hold: it is shown because no silent endpoint exists (not because the default switch holds out or the source can't be moved); no VB-CABLE device exists in any state (VC9 hardware ID); the PC is x64 (on ARM64, VC23). Otherwise the notice is as today. Running the setup while the cable exists would remove it (VC10), so presence is checked again right before launch.
- **VC22** What the button says and what shows with it. The button is the notice's one button in this state, in place of Show How. Next to it, before anything is fetched or installed, the notice names the product as "VB-CABLE by VB-Audio", links to the vendor (`https://vb-audio.com/Cable/`, where `www.vb-cable.com` leads, VC11), carries the licence's two required sentences verbatim, "The origin of VB-CABLE : www.vb-cable.com." and "VB-CABLE is a donationware, all participations are welcome.", and says in one line that Windows will ask for administrator permission, then VB-Audio's window opens and the user presses its Install Driver button (the setup's button label, from its strings `Install Driver` and "Ready to install ? Click the button right there..."). The exact words around the two required sentences are a UI proposal for the maintainer.
- **VC23** ARM64. On an ARM64 PC the notice shows today's text plus one honest line that AudioSync can't install the silent output on this PC yet, and no button. VC54 is evidence for a later change, not a switch this item turns on.
- **VC24** Nothing happens without the click. No download, extraction, prompt or device change starts before the user selects the button, and a click while an install is running does nothing.

### Install

- **VC30** Before anything else, the app reads the default playback and the default recording endpoint for each of the three roles (console, multimedia, communications) and keeps them for VC40. Source: [`IMMDeviceEnumerator::GetDefaultAudioEndpoint`](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immdeviceenumerator-getdefaultaudioendpoint).
- **VC31** Download. HTTPS from the pinned URL (VC1) only, with no redirect to another host, as the signed-in user, into a new empty folder under the app's own per-user data folder. It gives up after 15 seconds without a connection, 60 seconds in total, or past 4 MB. The notice shows that the download is under way.
- **VC32** Check. The zip's SHA-256 must equal the pinned value (VC2) before anything is extracted. Every file is then extracted into that folder, and each file is compared byte for byte with the verified zip and held open without write or delete sharing until the setup exits, so nothing can swap a file between the check and the elevated run. Nothing else is put in that folder.
- **VC33** Elevation. The app runs `VBCABLE_Setup_x64.exe` with no switches from that folder with the `runas` verb: one UAC prompt, showing VB-Audio's publisher (VC4). The vendor's window then opens and the user presses Install Driver there; AudioSync never presses it for them. AudioSync itself never runs elevated, imports no certificate and changes no trust setting. Source: [`ShellExecuteExW`](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shellexecuteexw).
- **VC34** Waiting. The app waits for the cable's endpoints to become active, not for the setup to exit: the vendor's window may stay open after the install, showing its result and its restart message (VC6), until the user closes it. The wait is 10 minutes from the UAC prompt, long enough for a person to read the vendor's window, press the button and sit through the few seconds the vendor warns it can look stuck (`readme.txt`); if the setup exits earlier with no endpoint, the wait ends 60 seconds after that exit. Success is the endpoints being there, not the setup's exit code (VC5). The notice says AudioSync is waiting for VB-Audio's installer meanwhile. An unelevated app cannot close an elevated window, so the vendor's window is always left to the user.
- **VC35** Failures. Each failure puts the notice back exactly as it was before the click (text and button) and adds one plain line, the same line until the next click:
  - UAC refused (`ERROR_CANCELLED`): Windows didn't allow the install, so nothing changed.
  - Download failed or timed out: VB-CABLE couldn't be downloaded; check the connection and try again.
  - Hash mismatch: the downloaded VB-CABLE isn't the version AudioSync checked, so nothing was installed. A file whose SHA-256 differs from the pin is never extracted or run, and it is deleted; a newer AudioSync carries a new pin.
  - Installer error (no cable device by the end of VC34's wait, also when the user closes VB-Audio's window without installing): VB-CABLE wasn't installed.
  - Cable device present but no active endpoint by the end of VC34's wait: VB-CABLE is installed; restart Windows to finish. In this state the button stays away (VC21), since the device exists.
  Each failure is logged with its cause (the debug log, not the notice).
- **VC36** After a success, with no restart: the app lists the devices again as Refresh Devices does (`desktop/src/adapter.rs:5894`), runs the routing check at once instead of on its next poll, and the existing code moves the default or the app's output to the cable (VC20). The notice goes when the routing check reports the source heard only through AudioSync, as today. While the stream runs, the source goes into the cable and is heard once.
- **VC37** The extracted folder is kept (about 3.5 MB) so the vendor's Remove Driver path stays available, unless VC53 shows that the Settings entry works without it; the zip itself is deleted after extraction.
- **VC38** Restart wording. The vendor's window asks for a restart in any case (VC6); that message is expected and AudioSync doesn't hide it. What the notice says after a success follows VC51's measurement: if the endpoints appeared and the sound moved with no restart, the notice says a restart is not needed; if VC51 shows a restart is needed, the notice says to restart Windows and the sound moves after it. Until VC51 has run, the text is the restart line.

### Defaults

- **VC40** From the click until 30 seconds after the cable's endpoints became active, every default (flow and role) that now points at a cable endpoint and pointed elsewhere at VC30 is set back to what VC30 read, if that endpoint still exists. Defaults the install didn't change are not touched. A default the user changes to the cable later is left alone. Source: VC8; the app already sets defaults in `desktop/src/audio/default_output.rs`.
- **VC41** VC40 runs before the default switch looks at the cable, so the record the switch keeps of "the default before streaming" (S470, S474) is the user's own device, never the cable.

### Lists

- **VC45** The cable's endpoints never appear where the user picks things: not as speakers, also not with Show Virtual Devices on, and "CABLE Output" not as an input source. Today they would: a Virtual output is listed while Show Virtual Devices is on or while it is turned on (`desktop/src/ui_model.rs:518-526`), and `input_sources` lists every active capture endpoint (`desktop/src/audio/capture.rs:526-557`). What changes: an endpoint whose device is VB-CABLE (hardware ID `VBAudioVACWDM`, or the device description "VB-Audio Virtual Cable" when the hardware ID can't be read) is left out of both lists. It is recognised by its device, never by the endpoint name (VC9). It stays a candidate for `silent_endpoint`. VB-CABLE A+B and C+D, and every other virtual output, are listed as today.
- **VC46** This applies to a cable the user installed before AudioSync too: AudioSync uses it as the silent output, and the user picks it in other apps, not in AudioSync.

### Removal and docs

- **VC47** The Windows help text gets one line on removal: VB-CABLE is removed under Settings > Apps > Installed apps (name as VC53 finds it), or by running VB-Audio's setup again and choosing Remove Driver, then restarting Windows (VC10). Without it, AudioSync shows the double-audio notice again.

## 3. Tests

### Unit tests (no hardware)

- **VC50** In `desktop/` unit tests, each against fakes:
  - the pinned URL and SHA-256 equal VC1 and VC2;
  - bytes with the pinned hash pass, the same bytes with one byte changed fail with the hash-mismatch state and nothing is extracted or launched;
  - the offer's text holds the two required sentences of VC22 verbatim, and the launch carries no command-line switches (VC33);
  - VC34's wait: endpoints appearing while the setup still runs is a success; no endpoint by 10 minutes, or 60 seconds after an early exit, is the installer failure;
  - the offer (VC21, VC23): button with no silent endpoint, no cable, x64; no button when the default switch holds out, when a cable device exists (even disabled), or on ARM64;
  - each failure in VC35 returns the notice to its state before the click with its one line, and a second click while busy does nothing (VC24);
  - success lists devices again and runs the routing check at once (VC36);
  - VC40: only defaults moved to a cable endpoint after the click are set back, only to an endpoint that still exists, and a later move by the user is left alone; VC41's order;
  - VC45: a VB-CABLE endpoint named "Speakers (VB-Audio Virtual Cable)" is recognised by its device; it is in neither the speaker list (Show Virtual Devices on or off) nor `input_sources`, and `silent_endpoint` still picks it; an endpoint of "VB-Audio Cable A" is listed as today.

### Hosted-runner proof

- **VC51** Red, on a clean `windows-latest` runner. The runner has no audio endpoint, so it gets one as `scripts/stranger/windows_default_device.ps1:296-315` does: the Scream sound card (MS-PL, checked by hash, runner only) on a software-enumerated device, which AudioSync lists as the PC's own speaker, not Virtual. Scream sends what it plays as UDP to 127.0.0.1, so a recorder on that port hears exactly what the PC's speakers would play; no physical speaker is needed. A player plays the click train of `scripts/stranger/heard.py` on the default output, and AudioSync streams All System Audio to the airplay crate's `stranger_rx` receiver (`airplay/examples/stranger_rx.rs`), run in a Windows container because discovery drops the computer's own addresses, which writes what it would play to a recording. Red when both recordings hold the click train: heard on the PC and on the receiver, the receiver's copy later by an offset the job records. This is today's behavior and fixes the baseline.
- **VC52** Green, same job, continued, in two legs, and the job summary states which leg produced the heard-once result. The click-path leg is the shipped path: the notice's button is invoked through UI Automation (on the runner only), the UAC prompt is absent because the runner's account runs elevated without one, the vendor's window opens and a left click posted to its window presses Install Driver, since the vendor paints that button itself and UI Automation sees none. If that window can't be driven, the unattended leg installs the same verified package through `pnputil` and `devcon`, as the 18 Nov calibrate-loop job did (commit 9027db37e), and the app then finds the cable as it would after a click. Then the player is restarted, since a player opened before the cable keeps its old device, as any app may; a take with the first player still running is kept as a record only, and the job summary names the player's audio API (Media.SoundPlayer, which is waveOut, MME) and whether it followed the default move. With the restarted player, the Scream recording holds the click train exactly once, and that copy is the synced one: each click is one peak, landing within 50 ms of the receiver's (S50's dead band, how far apart two outputs may sit), with nothing at the click threshold within that margin of the red phase's offset before it. A single early copy, the undelayed one, fails. The receiver's recording holds the train exactly once (`heard.py check`), and the job also records the defaults before and after (VC40) and the endpoint list (VC45: no cable row in the UI tree). In the click-path leg the job fails if any Windows dialog blocks the install (a run that reaches the end of VC34's wait is red, which is how a second dialog, VC5, shows up). A restart is never part of the job, so a pass in the click-path leg also settles VC38's wording.
- **VC53** Removal on the same runner after VC52: the Uninstall entry's display name and command are written to the job log; running it removes the device (UI Automation presses the vendor's Remove Driver if its window opens) (after the job's wait, with a restart if needed, which a runner can't do, so a "restart required" result is logged, not failed), and AudioSync shows the double-audio notice again on the next routing check.
- **VC54** ARM64: VC51 and VC52 again with the ARM64 build on GitHub's `windows-11-arm` hosted runner, which public repositories can use; no workflow of this repository uses it yet. It is tried within this item; if the runner isn't available or the run fails, the row is logged as untested. Either way VC23 stays as written.
- **VC55** What the runner can't show: a real PC whose sound driver Windows prefers over the cable, and the UAC prompt itself. Those are checked once by hand on a clean Windows 11 VM with a sound device and recorded; neither gates (VC40 is covered by unit tests either way).

## 4. Notices and docs wording

- **VC60** `THIRD_PARTY_NOTICES.md` gets a VB-CABLE entry that says: AudioSync doesn't ship VB-CABLE; on the user's click it downloads VB-CABLE by VB-Audio (Vincent Burel) from the vendor and runs the vendor's installer unmodified; the origin is www.vb-cable.com; VB-CABLE is donationware and all participations are welcome; use in a company or institution needs licences bought from VB-Audio; the link to the licensing page. No VB-Audio licence text is copied in, since nothing of it is redistributed.
- **VC61** The README's Windows part and `desktop/README.md` say in one or two plain sentences that on a PC without a virtual output AudioSync offers to install VB-CABLE by VB-Audio (donationware, link) so the PC doesn't play the sound twice, that Windows asks for administrator permission once, and how to remove it (VC47). [WINDOWS_AUDIO_ROUTING.md](WINDOWS_AUDIO_ROUTING.md) gets its "doesn't install" sentence and its deferral of bundling updated to point here.
- **VC62** The notice and help text go through `strings.slint` like all app text; they name VB-Audio's product and the vendor, never claim AudioSync made or vouches for the driver, and carry no donation pitch beyond the licence's two required mentions.

## 5. Where the decisions don't fully hold yet

- **VC70** One prompt: expected (VC5) but unproven until VC52; the vendor's forum reported a second Windows dialog with older packs. If VC52 shows one, the flow is one UAC prompt plus one Windows dialog, and the notice text says so; the app never suppresses it (VC33).
- **VC71** No restart: the vendor says to restart (VC6); a runner install without one worked through `pnputil`. VC35's last line covers the PC that does need one.
- **VC72** ARM64: supported by the vendor, installed through an x64 setup under emulation, unproven (VC7). The honest line stays (VC23); VC54 is tried, else logged as untested.
- **VC73** Licence wording: the licensing page allows distributing the package as is with an application and a silent install; the 2024 `readme.txt` in the same zip still asks for the author's agreement for integration into another installer (VC11). The shipped path doesn't integrate it into an installer: it downloads the package as is and opens the vendor's own setup window, where the user installs (VC33).
- **VC74** Microsoft Store: policy 10.2.4 restricts depending on non-Microsoft drivers ([WINDOWS_AUDIO_ROUTING.md](WINDOWS_AUDIO_ROUTING.md), Installer impact). A Store build, if one is made, may need the button left out.
