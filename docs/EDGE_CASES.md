# Edge cases

What AudioSync does when the world changes under a running session, where the code that handles it lives, and how each case is checked. Cite a case by its ID (EC1 to EC13); the IDs don't change when cases are added.

"Automated" names the checks in `Tests/` that cover the decision logic; every logic check for a case starts with its ID, so `Tests/run-tests.sh | grep EC7` lists them. Ring-buffer checks are cited by name too, but the test run only prints the ring suite's summary, so their names show up only when one fails. Anything that needs a person (unplugging a device, Bluetooth, sleep, changing a device's format, the network) is under "Manual". The manual steps play audio, so do them at a sensible volume.

|---|---|---|
| EC1 | Device unplugged and replugged during playback | Automated (logic) and manual |
| EC2 | Bluetooth disconnect and reconnect | Automated (logic) and manual |
| EC3 | Sleep and wake | Automated (core) and manual |
| EC4 | Sample-rate change on an output | Automated (logic, core) and manual |
| EC5 | Switching the source during playback | Automated (logic, core) and manual |
| EC6 | The source app quits | Automated (logic) and manual |
| EC7 | The AirPlay sender stops after an internal error | Automated (logic) and manual |
| EC8 | Every speaker off, then on | Automated (logic) and manual |
| EC9 | The default output changes | Automated (logic) and manual |

The reconciles mentioned below are `reconcileAirPlaySpeakers()` (`AppDelegate+AirPlay.swift`) and `reconcileLocal()` (`AppDelegate+Outputs.swift`). Events run them (S101): Core Audio's device-list notice (`AppDelegate.observeDeviceList`, bursts merged over 0.3 s) and a lost output run `reconcileLocal()`; the launch, Refresh Devices, Retry and the sender's own discovery changes and speaker events cover the AirPlay side; a wake runs both; a restart of the sender after a failed start, a denied Local Network answer to ask again and the Local Network hint get one reconcile when they fall due (`AppDelegate.scheduleDueReconcile`). A safety net (`AppDelegate.startSafetyNet`) runs both every 30 s for what no event reports.

## EC1: Device unplugged and replugged during playback

Expected: the unplugged speaker goes silent and leaves the list; every other speaker keeps playing and streaming stays on, even when it was the only speaker. The speaker stays switched on, so as soon as macOS lists the device again after it's plugged back in, it plays again at its own delay and volume, with no notice. If the unplugged device was the input-device source, streaming stops with the notice "The input device was disconnected, so streaming has stopped."

Code path:
- `OutputRenderer.installDeviceAliveListener` sees `kAudioDevicePropertyDeviceIsAlive` go to 0 and calls `onDeviceGone`; `StreamEngine.handleOutputLost` removes that renderer and reports `onOutputGone` (`AppDelegate.handleEngineEvents` logs it and lists the devices again at once; the speaker stays in `enabledLocal`).
- `reconcileLocal()` drops the device from the list while it's gone and lists it again when Core Audio's device-list notice says it returned (or at the 30 s safety net, should no notice come); `syncLocalOutputs()` uses `LocalOutputSync.plan` (`SpeakerState.swift`) to attach it again by UID (the device's Core Audio ID may change).
- `StreamingPolicy.isIdle` (`SpeakerState.swift`) keeps streaming on while a speaker is on, present or not.
- Input-device source: `SourceCapture.watchInput` sees `kAudioDevicePropertyDeviceIsAlive` go to 0 or the device leave the device list, stops its IOProc and raises `.sourceLost(.inputDisconnected)`; the `engine.onInterrupted` handler in `AppDelegate.swift` stops streaming and posts the `Notice.source` notice.

Automated: "EC1 unplug: a playing speaker that is still present is left alone", "EC1 unplug: a lost speaker stays on and waits while its device is missing", "EC1 unplug: streaming keeps running while the only speaker is unplugged", "EC1 replug: the speaker is attached again once its device is listed", "EC1 switch off: a speaker turned off is detached", "EC1 new ID: a playing speaker whose device came back under a new ID is restarted on it", "EC1 new ID: a sync stops the renderer bound to the old ID and starts it on the new one" (and the other "EC1 new ID: …" checks); core `a_replugged_output_never_replays_what_it_played_before` (`core/src/reader.rs`).

Manual: stream to a USB audio device and one other speaker. Unplug the USB device: the other speaker plays on, the USB row disappears. Plug it back in: as soon as macOS shows the device again (in Sound settings, say), the row returns, switched on, and plays in sync again. Repeat with the USB device as the only speaker: streaming stays on while it's unplugged and resumes on replug. With a USB microphone as the source, unplug it: streaming stops with the notice above.

Note: detaching normally relies on Core Audio's "is alive" notification. Should a device vanish without one and come back under a new Core Audio ID, its renderer would still be bound to the dead ID. The host keeps the ID each output was started on (`localBoundDevices`), so the next sync (the device-list notice, or the 30 s safety net) sees the UID listed under another ID and `LocalOutputSync.plan` restarts it: the old renderer stops and a new one starts on the listed device at the speaker's delay and volume. A playing speaker whose UID isn't listed is left alone until it is.

Windows: the same, with the device list as the signal too: an output stops when its stream fails or when the list no longer shows its device, and one whose stream died while Windows still listed it gets the disconnected notice once the list drops it. A USB device plugged into another USB port comes back under a new endpoint ID. When that ID is new to this run (or one a moved device left behind) and exactly one output with the same name and kind was listed earlier in this run and is gone now, and that one has something set, the new ID takes over its switch, volume, delay, auto-connect mark and groups, and the old ID is forgotten. With two identical devices gone, set or not, the new one starts out as a new speaker, and an ID listed before in this run (a second display of the same model waking first) never takes over another one's settings. Windows may number a device in another port, or a second device of the same model, inside the parentheses ("Speakers (2- USB DAC)"); names are compared without that number, so a moved DAC it numbers keeps its settings, and two of the same model, numbered or not, still count as identical devices. A speaker saved as on that no listing has shown since launch (an old endpoint ID, say) doesn't count as on until it's listed, so switching off every listed speaker stops streaming and a start asks for a speaker (S162). Automated: `an_output_lost_while_still_listed_is_lost_again_once_the_listing_drops_it` (`desktop/src/audio/controller.rs`), `a_usb_speaker_plugged_into_another_port_keeps_its_settings_under_its_new_id`, `settings_follow_a_new_id_only_from_the_one_absent_speaker_of_its_name`, `a_new_id_doesnt_take_settings_when_an_untouched_twin_left_too`, `a_twin_listed_before_that_comes_back_first_doesnt_take_the_others_settings`, `a_port_a_moved_speaker_left_counts_as_new_only_until_it_is_listed_again`, `a_usb_speaker_windows_numbers_in_another_port_keeps_its_settings`, `twins_windows_numbers_apart_still_count_as_twins`, `twins_windows_numbers_apart_that_appear_together_dont_take_settings` and `a_speaker_on_that_wasnt_listed_since_launch_doesnt_count_as_on` (`desktop/src/adapter.rs`). Manual: stream to a USB DAC, then move it to another USB port. Within a few seconds its row comes back switched on, at its volume and delay, and plays; the disconnected notice clears.

## EC2: Bluetooth disconnect and reconnect

Expected: the same as EC1. A headset that drops out (out of range, powered off, taken by another device) goes silent and leaves the list; the rest keep playing. When it reconnects it plays again as soon as macOS lists it. A headset switching to its hands-free profile (another app opens its microphone) changes its sample rate; see EC4.

Code path: the same as EC1 (`OutputRenderer` alive listener, `StreamEngine.handleOutputLost`, `reconcileLocal()`, `syncLocalOutputs()`, `LocalOutputSync.plan`). A Bluetooth headset used as the input-device source follows the input path in EC1. Auto-connect (`AppDelegate+Groups.swift`, `autoConnect`) turns a reappearing speaker on when it's marked for auto-connect.

Automated: "EC2 Bluetooth: a disconnected headset waits; the other speaker keeps playing", "EC2 Bluetooth: a reconnected headset is attached again"; the "EC2 Bluetooth fresh link: …" checks (S325); plus the EC1 checks.

Manual: stream to Bluetooth headphones and one other speaker. Turn the headphones off: the other speaker keeps playing, the headphones' row disappears. Turn them on again: the row comes back switched on and plays in sync within a few seconds. A Bluetooth speaker that starts playing right after its link came up goes quiet once, about 2 s in, for about a second, then plays in sync (S325). Repeat with the headphones marked for auto-connect and switched off in AudioSync before the disconnect: on reconnect they switch on by themselves.

## EC3: Sleep and wake

Expected: nothing plays while the Mac sleeps. After wake, streaming is still on and the local speakers continue with fresh audio at their configured delay, never the audio from before the sleep. AirPlay speakers that were on stay on, with no notice: a speaker whose session didn't survive the sleep gets a new one from the sender by itself (after 1, 2, 4, 8 and 16 s, then every 30 s) until it plays. A speaker that was switched off stays off. Devices that disappear across sleep (USB hubs, Bluetooth) follow EC1 and EC2, and an AirPlay speaker that left the network follows EC12.

Code path:
- `AppDelegate.observeSleepAndWake` (`AppDelegate+AirPlay.swift`) sets `macAsleep` on `NSWorkspace.willSleepNotification` and clears it on `didWakeNotification`; `screensDidWakeNotification` counts as a wake too while AudioSync still thinks the Mac is asleep, in case the wake notification goes missing. While the Mac sleeps, `reconcileAirPlaySpeakers()` asks the sender nothing; on wake it runs at once, so the sender's speakers match the switches again (`syncNativeSpeakers`), and `reconcileLocal()` lists the devices that came or went during the sleep.
- Core Audio stops and resumes the capture IOProc (`SourceCapture.IOLink`, on the tap's aggregate device or the input device) and the renderers; the core's delay reader (`CoreDelayReader`) plays silence while nothing arrives and re-establishes the delay without replaying old audio.

Automated: core `a_writer_stall_above_the_dead_band_holds_silence`, `a_reader_that_ran_dry_plays_new_frames_as_they_arrive` and `stall_resumes_after_the_last_frame_at_the_exact_delay` (`core/src/reader.rs`). Mac logic checks (`Tests/logictest.swift`): "output stall and capture watch: neither fires from the will-sleep notice to the wake, and both count 2 s from the wake" and "capture watch: a service restart during the sleep still closes the capture, and its first try comes 1 s after the wake".

Windows: right after a wake (or a format change), Windows may refuse to open an endpoint for a moment while it rebuilds it (`AUDCLNT_E_ENDPOINT_CREATE_FAILED`, `AUDCLNT_E_RESOURCES_INVALIDATED`). That counts like a device that went away: the output stays on and is tried again at every poll, with no notice, instead of being switched off with a "couldn't start" notice at once. If Windows still lists the device and keeps refusing it for about 30 s, the output stays on, shows the notice of a lost speaker and is tried again about every 3 s (about every ten seconds after a try that doesn't answer) until it opens, which clears the notice, or the user switches it off; any other error at open still switches it off with the "couldn't start" notice at once. An audio thread whose start doesn't answer within 5 s (a hung device activation) is given up, so a device that doesn't answer holds the window for at most about 5 s each time it is tried; an output stays on and is tried again about every ten seconds, and a thread that answers after all stops its stream at once. The outputs still to start in that pass aren't tried then (Windows audio is most likely not answering at all): they wait the same ten seconds, and next time they go before the ones that hung. The same 5 s bound covers an output's own Windows volume, whose every call (starting the thread that makes them, registering the change listener, a read after Windows reports a change, and the fix's read and writes) runs on a thread of its own: when one doesn't answer in time, the output shows no device-volume hint for now and isn't read, it is tried again about every ten seconds (said once in the debug log, not at every try), a listener registered late after all is removed at once, and while that call still hangs the other outputs' calls aren't waited for. A fix click then writes nothing, or stops after the write that hung (a muted output whose level write hung isn't unmuted either). Quitting waits for an output's volume thread as long as for one answer, at most 5 s: a thread still busy removing a listener is left to finish on its own. Automated: `an_endpoint_windows_rebuilds_after_a_wake_or_a_format_change_is_tried_again` and `a_thread_that_doesnt_answer_in_time_is_given_up_and_its_late_start_undone` (`desktop/src/audio/wasapi/com.rs`), `an_output_whose_device_doesnt_answer_stays_on_and_is_tried_again_seconds_later`, `once_a_start_doesnt_answer_the_other_starts_of_that_pass_wait_their_turn`, `a_healthy_output_isnt_kept_waiting_behind_one_that_keeps_hanging`, `stopping_ends_the_wait_for_an_output_that_didnt_answer`, `an_output_whose_listed_device_keeps_refusing_stays_on_and_is_tried_every_3_s`, `a_refused_try_that_doesnt_answer_waits_10_s_and_the_next_refusal_3_s`, `a_refused_output_that_then_fails_hard_is_turned_off_at_once`, `switching_off_a_refused_output_ends_its_tries_and_its_notice` and `a_stalled_output_that_opens_after_a_refusal_keeps_its_notice_until_five_seconds_of_play` (`desktop/src/audio/controller.rs`), `a_speaker_windows_keeps_refusing_shows_the_lost_notice_until_it_plays` (`desktop/src/adapter.rs`), `a_volume_listener_that_doesnt_answer_in_time_is_given_up_and_its_late_registration_undone`, `a_volume_read_or_fix_that_doesnt_answer_in_time_is_given_up_without_freezing_the_caller`, `a_volume_thread_that_doesnt_start_in_time_holds_no_later_start` and `a_volume_thread_that_hangs_unregistering_a_listener_doesnt_hold_quitting` (`desktop/src/audio/wasapi/volume.rs`), `an_output_whose_volume_listener_doesnt_answer_shows_no_device_volume_until_a_later_try`, `a_device_volume_read_that_doesnt_answer_shows_none_until_a_later_try` and `a_fix_that_windows_audio_doesnt_answer_shows_no_device_volume_until_a_later_try` (`desktop/src/audio/controller/device_volume.rs`).

Manual: start AudioSync with the debug log on (`docs/DEVELOPMENT.md`). Stream to a local speaker and two AirPlay speakers with some music playing, then switch one AirPlay speaker off. Put the Mac to sleep from the Apple menu, wait at least five minutes, wake it. Expected: streaming is still on, the local speaker resumes with fresh audio, the AirPlay speaker that was on plays again in sync within about half a minute, still switched on and with no notice, and the other one stays off. In sync means at the same delay setting as before the sleep, with no extra lag on the AirPlay speaker. No old audio is replayed. The debug log shows "going to sleep" and "woke from sleep". Repeat once with a long sleep (lid closed for an hour or overnight, on power so Power Nap can run): same result. Then unplug the AirPlay speaker while the Mac sleeps and wake it: it leaves the list and stays switched on (EC12); plugged back in, it plays again. If a speaker that was on is turned off with a notice after a normal wake, attach the debug log.

## EC4: Sample-rate change on an output

Expected: a local speaker whose device changes rate or channel count starts again in the new format right away, with a short gap on that speaker only, at the same delay and with no notice. When the change also changes the capture rate (the tap's format follows the output; an input-device source can be switched to another rate), streaming rebuilds itself at the new rate: a short dropout on every speaker, then playback resumes with the same delays and no notice.

Code path:
- Each `OutputRenderer.start` makes the core's renderer for the rate its device runs at then and gives the output unit that rate, so the renderer converts from the capture rate (S62) and its fades count device frames. Each output also listens for its device's nominal rate and output stream configuration; when either differs from what its start read (`OutputFormatWatch`), `StreamEngine` drops it without a fade and `AppDelegate` starts it again by UID at its current hold-back in the same main-queue turn, its start lead held meanwhile (S330, S328).
- `SourceCapture` listens to `kAudioTapPropertyFormat` and the aggregate device's `kAudioDevicePropertyNominalSampleRate` (tap), or the input device's `kAudioDevicePropertyNominalSampleRate`; `CaptureRate.running` takes the rate of the device the IOProc runs on (the tap's own rate only when that can't be read) and `CaptureRate.needsRestart` (`CaptureCheck.swift`) decides; an app tap built again for new processes goes through the same rule; `.formatChanged` goes through `StreamEngine.handleInterruption` to the `engine.onInterrupted` handler in `AppDelegate.swift`, which calls `startEngine(origin: .automatic)`.
- Delays are kept in milliseconds and converted at the new rate (`OutputRenderer.setDelay`); AudioSync's AirPlay sender gets the new rate at the rebuild and resamples to 44.1 kHz itself (`NativeAirPlayTap.prepare`).

Automated: "EC4 rate: a new capture rate rebuilds the session", "EC4 rate: a higher capture rate rebuilds the session", "EC4 rate: the same rate keeps playing", "EC4 rate: an unreadable rate keeps playing", "EC4 rate: a format change rebuilds the session the engine stopped, unless the user switched streaming off"; logic "capture rate: …", "output format: a running output reopens once its device reports another rate or channel count, never for a notice that changes neither", "output format: a format change during a stall trial reopens as a format change and leaves the trial as it was"; core `core/tests/drift.rs` (drift both ways stays within the tolerance).

Manual: stream to a USB output and an AirPlay speaker. In Audio MIDI Setup, change the USB output's format from 48,000 Hz to 44,100 Hz and back. Expected: at most a short glitch, then in sync with AirPlay, no notice. Do the same on the Mac's default output device: a short dropout everywhere, then playback resumes in sync; the debug log shows "capture rate changed".

## EC5: Switching the source during playback

Expected: choosing another source while streaming gives a short gap, then only the new source plays on every speaker that was on. AirPlay and Cast speakers stay connected through the switch (only the capture is rebuilt), so a speaker that asks for a code doesn't ask again; nothing from the old source is replayed. If the new source can't start (an input device while microphone access is off, or an app that quit between the click and the start), the old source plays on under the same speakers and a notice says so (an alert for the microphone); streaming stops only when the old source can't start again either. While macOS asks for the microphone, the old source stays shown and keeps playing until the answer. While streaming is off, a new source is only remembered for the next start.

Code path: `AppDelegate.setSource` (`AppDelegate+Outputs.swift`) asks `SourceSwitch.decide` (`AudioSource.swift`); `.restart` calls `startEngine(origin: .user, switching:)` (`AppDelegate+Engine.swift`), which stops only the capture, keeps the AirPlay and Cast speakers, and asks `CaptureSwitch` what a failed start falls back to. `StreamEngine.stop` resets the ring; `SourceCapture.halt` stops and destroys the capture IOProc at once, and `SourceCapture.start` builds a tap for the new source. The old tap and its aggregate device are destroyed on the main queue's next turn, after the new tap exists (`CaptureClose`, `CaptureSupport.swift`): a tap made right after the old one was destroyed failed, and the old tap keeps the old source muted until the new one takes over.

Automated: "EC5 source: switching while streaming rebuilds the capture", "EC5 source: switching to an input device while streaming rebuilds the capture", "EC5 source: switching while stopped only remembers the choice", "EC5 source: choosing the same source changes nothing", and the "EC5 source: …" tests of a switch that keeps the speakers or falls back (S141); logic "capture close: a source switch makes the new tap before the old tap is destroyed"; every session gets a new core ring (`EngineParts.make`).

Manual: stream the whole system with music in one app and a video in a browser. Switch the source to the music app: after a short gap only the music plays, AirPlay speakers stay on. To see the failure path, turn off AudioSync under System Settings → Privacy & Security → Microphone, then switch the source to an input device: an alert says so, a notice stays, and streaming stops. (The source list only offers running apps, so a not-running app can't be picked by hand.)

## EC6: The source app quits

Expected: with the setting off (Windows' default), when the app chosen as the source quits while streaming, streaming stops, the AirPlay speakers are released, and the notice "<App> quit, so streaming has stopped." appears. The speakers stay switched on (shown as waiting) and the source stays that app, so pressing Start after reopening it streams again. Quitting any other app changes nothing; the whole-system and input-device sources never stop because an app quits. With AudioSync > Switch to All System Audio When the Source App Quits on (S227), the Mac's default since 0.7.1, streaming goes on with All System Audio instead, the AirPlay speakers stay on, the source is stored as All System Audio and the notice reads "<App> quit, so AudioSync switched to All System Audio." Reopening the app doesn't switch back.

Code path: the `NSWorkspace.didTerminateApplicationNotification` observer (`AppDelegate.observeApps`) asks `AppLifecycle.sourceQuit` (`AppLifecycle.swift`), which asks the core (`SourceQuit.decide`, `asc_source_quit_decide`), then `AppDelegate.sourceAppQuit` either calls `stopEngine()` and posts `Notice.source`, or, with AudioSync > Switch to All System Audio When the Source App Quits on, goes on with the whole system and posts its notice (S227). `SourceCapture.followApp` may see the app's audio processes vanish first (`AppTapFollow`, `CaptureSupport.swift`): while the app still runs it drops the tap and waits for a new audio process (when only some of them change, `AppRetap` changes the running tap's description in place, or builds the new tap before closing the old one, so the app never plays unmuted); once the app is gone, or if it can't build the new tap, it raises `.sourceLost(.appNotRunning)`, which `AppLifecycle.sourceQuit` treats as the same quit, so it ends in the same stop or switch and only one notice shows.

Automated: core `only_the_source_apps_own_quit_ends_the_session` (`core/tests/policy_capture.rs`, `depends_on_app`) and the S227 core tests in `core/tests/policy_source_quit.rs`; logic "EC6 app quit: the source app quitting while streaming stops the session", "EC6 app quit: the whole-system source never ends on a quit, under either setting (S164, S227 b)", "EC6 app quit: an app without a bundle ID changes nothing, under either setting (S164)", "EC6 app quit: the source app quitting while stopped changes nothing, under either setting (S227 a)", "EC6 app quit: another source, another app or an app without a bundle ID keeps streaming (S227 b)", and the "source quit: …" checks; logic "app tap: …" (the tap follows the app's audio processes, waits while there are none and loses the source once the app is gone).

Manual: turn off AudioSync > Switch to All System Audio When the Source App Quits, choose Music as the source and stream it. Quit Music: streaming stops with the notice above, the speakers show as waiting. Reopen Music, press play and Start: streaming resumes. With the whole system as the source, quit an app that is playing: streaming continues. Turn on AudioSync > Switch to All System Audio When the Source App Quits, choose Music again, stream and quit Music: the speakers keep playing other apps' sound, the picker shows All System Audio and the switch notice appears; reopening Music leaves the source on All System Audio.

## EC7: The AirPlay sender stops after an internal error

The sender runs inside the app, so there's no separate process to restart. If it stops after an internal error, its speakers leave the list (their switches stay as they are), the Local Network probe stops, the local speakers stop waiting for AirPlay, and a notice says the sender stopped; the AirPlay section offers Retry. Retry starts a new sender, which finds the speakers again, plays to the ones switched on and gets the current track info sent again. A sender that can't start at all is tried again every 10 s or so, with one notice.

Code path: the core catches a panic at its C interface and reports `ASC_AIRPLAY_EVENT_FAILED` once; `nativeSenderFailed` (`AppDelegate+NativeAirPlay.swift`) drops the sender, and `NativeSenderStarts` (`NativeAirPlayModel.swift`) keeps it from starting again by itself until Retry (`retryNativeAirPlay`). A start that fails is retried by `reconcileNativeAirPlay` in the reconcile that falls due `NativeSenderStarts.retrySpacing` later (`NativeSenderStarts.restartAt`, armed by `AppDelegate.scheduleDueReconcile`).

Automated: "EC7 native airplay: the sender's failure event makes the app drop it and offer Retry", "EC7 native airplay: a sender that stopped after an internal error doesn't restart by itself", "EC7 native airplay: a sender that stopped schedules no restart; only Retry starts one (S101)", "EC7 native airplay: it shows as failed, with Retry", "EC7 native airplay: Retry starts a new sender at once", "EC7 native airplay: a failed start is told once", "EC7 native airplay: after a failed start, a later reconcile starts it again, not a sooner one", "EC7 native airplay: the restart falls due exactly when a reconcile may start the sender again (S101)".

Manual: a release build gives no way to make the sender fail on purpose. If the debug log ever shows "native AirPlay: the sender stopped after an internal error", usually with where it panicked in parentheses ("panic at <file>:<line>" for a call the core caught, or "latest panic at <file>:<line>" when the sender's own thread ended, the latest panic the process saw), keep that line for the bug report and check that the notice and Retry appear, that local speakers keep playing, and that Retry brings the AirPlay speakers back.

## EC8: Every speaker off, then on

Expected: switching off the last speaker stops streaming and releases the AirPlay speakers; the source app's own audio is no longer muted. Switching any speaker on again starts streaming to it, with fresh audio only. Turning streaming on with no speaker on starts it anyway, with no alert: the speaker list says "No speaker is on. The first one you turn on starts playing." and the first speaker turned on joins; that session keeps running until a speaker has been on and the last one goes off. A start AudioSync makes on its own with no speaker on posts "Turn on at least one speaker first (under This Mac or Connected Speakers)." as a notice. On a first install, This Mac starts on, once.

Code path: `setLocalEnabled` (`AppDelegate+Outputs.swift`) and `setNativeAirPlayEnabled` (`AppDelegate+NativeAirPlay.swift`) start streaming through `StreamingPolicy.startsStreaming` and stop it through `stopIfIdle()` with `StreamingPolicy.isIdle` (`SpeakerState.swift`); `startEngine` checks `StreamingPolicy.hasSpeaker` and `StreamingPolicy.startsWithoutSpeaker` first. `stopEngine()` and `StreamEngine.stop` (ring reset) end the session.

Automated: "EC8 all off: streaming stops when the last speaker is switched off", "EC8 all off: one AirPlay speaker still on keeps streaming", "EC8 all off: nothing to stop while stopped", "EC8 all off: turning a speaker on again starts streaming", "EC8 all off: only a switch-on while stopped starts streaming", "EC8 all off: an automatic start with no speaker on asks for one first", "no speaker on: the power switch starts streaming anyway, with no alert; an automatic start still waits", "no speaker on: a session started with every speaker off keeps running", "first install: This Mac starts on"; logic "speaker: click on a waiting speaker turns it on (and starts streaming)"; every session gets a new core ring (`EngineParts.make`).

Manual: stream to two speakers. Switch both off one by one: streaming stops after the second, the source app is audible on the Mac's own output again. Switch one on: streaming starts on that speaker alone, without a burst of old audio.

## EC9: The default output changes

Expected: changing the Mac's sound output (Control Center or System Settings) while streaming changes nothing in AudioSync: every chosen speaker keeps playing, the source stays muted on the new default device (no doubled audio), and the speaker list doesn't change. If the new default device runs at a different rate, the capture rebuilds as in EC4. While streaming is off, other apps simply play on the new default.

Code path: AudioSync doesn't follow the default output. Each `OutputRenderer` is bound to its own device ID; the tap built in `SourceCapture.TapObjects` captures processes, not a device, and mutes their own playback wherever it goes (`muteBehavior = .muted`). A format change on the tap goes through `CaptureRate.needsRestart` (EC4). `AudioDevices.defaultOutputDevice()` exists but nothing in the session uses it.

Automated: the EC4 checks ("EC4 rate: …"). Nothing else here is decision logic; the rest is manual.

Manual: stream the whole system to an AirPlay speaker and a USB speaker, with the Mac's built-in speakers as the default output. Switch the default output to the USB speaker, then to headphones, then back. Expected: no interruption longer than a brief rebuild, nothing doubled on the new default device, the speaker rows unchanged.

## EC10: Six or more speakers

Expected: every speaker is listed, This Mac first and the rest by name; all of them can be on at once and play in sync. The menu bar panel scrolls once its rows don't fit (it shows at least six rows); the main window scrolls too.

Code path: `SpeakerLayout.split` (`SpeakerLayout.swift`) orders the rows; the menu bar panel switches to a `ScrollView` above `maxListHeight` (`MenuBar.swift`).
