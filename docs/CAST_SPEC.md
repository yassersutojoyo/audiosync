# AudioSync Google Cast sender specification

A behavioral specification for a Google Cast audio sender in AudioSync: a component that finds Cast devices on the local network, starts Google's Default Media Receiver on one of them, and has it play the host's live audio, fetched over HTTP from the host. It is written so the sender can be built by someone who reads only this document, the RFCs and format documents it cites, Google's public Cast documentation and the documentation of the crates they choose.

The sender drives one Cast target at a time: a single device, or a Cast group driven as one target. Several independent Cast devices in one stream are noted as a gap (section 9), and so is what only a real group can settle. The sender never claims sample-accurate sync with local speakers or AirPlay receivers: section 7 says what it can and cannot control.

Provenance. Written on 2026-10-21 from public sources: Google's Cast developer documentation and support pages, community protocol write-ups, and the observed behavior of open-source Cast senders (pychromecast, go-chromecast, catt, mkchromecast and the node castv2 module), read as behavior and restated in our own words. No code, and no paraphrase of code, from any of them is in this document. The group clauses (C89 to C103) were added on 2026-10-22 on the same terms, from Google's support pages, Google's Android sender reference, Google's Open Screen library, pychromecast and the Home Assistant Cast integration. Device authentication is described only as what a sender sees and whether a receiver requires it; nothing here describes how to forge or bypass it.

## Conventions

- MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are normative, in the sense of RFC 2119.
- Each clause states one behavior of the sender. It ends with *Source:* (the kind of source the fact comes from; "derived" means computed or reasoned from facts in the cited sources rather than stated there) and, where AudioSync needs something the sources don't settle, *Required:* (the choice the sender MUST implement). "*Source:* AudioSync design" marks a clause that is a requirement only.
- A *Source:* of "observed behavior of open-source senders" reports what such a sender does, as read in its source or documentation. It is one implementation's reading of the protocol, not Google's, and several senders agreeing doesn't make a behavior Google's either.
- Latency figures marked "user reports" come from issue trackers. They are single observations on unnamed setups, quoted to show the order of magnitude and the spread, never as a specification.
- Terms: *sender* is the component this document specifies; *device* or *receiver* is the Cast device; *platform* is the device's built-in endpoint `receiver-0`; *app* is a receiver application running on the device, here the Default Media Receiver; *channel* is one TLS connection from the sender to one device; *session* is one channel plus the app it launched and the HTTP stream the app fetches, from connect to teardown; *host* is the AudioSync app that drives the sender; *stream server* is the HTTP server inside the sender that serves the audio.
- Message names and JSON field names are written as they appear on the wire, such as `GET_STATUS` and `transportId`; they are case-sensitive.
- Example addresses use 192.0.2.0/24 (RFC 5737).
- Clause IDs run from C1 without gaps in this version. A clause added later takes the next free number and sits in the section it belongs to; a dropped clause keeps its number, marked withdrawn.

## 1. Scope and role

- **C1** The sender handles audio only. It never loads video, images as the main media, or text tracks; artwork is sent only as part of track metadata (C53). *Source:* AudioSync design.
- **C2** A stream drives at most one Cast target in this version: one device, or one group (C3). Starting a stream on a second Cast target while one is playing, a member of the playing group included, is refused with a clear reason; the sender never runs two Cast sessions side by side. *Source:* AudioSync design; G2 tracks lifting the limit.
- **C3** A Cast group (several devices that Google software plays in step as one target) is driven as one target: one channel to the group, one Default Media Receiver session, one volume control and one measured offset (C89 to C103). The sender never drives a group's members one by one to imitate group playback. *Source:* AudioSync design; observed behavior of open-source senders [pychromecast] (a group handled like a single device); Google support FAQ [google-group-faq]. G1 lists what only a real group settles.
- **C4** The sender uses only the Default Media Receiver app (C39). It never registers, hosts or launches a custom receiver app, and never needs a Google developer account. *Source:* AudioSync design; Google Cast Web Receiver overview [cast-receiver] (the Default Media Receiver needs no registration).
- **C5** Encrypted or DRM-protected media, and anything that needs a Custom Receiver, are out of scope. *Source:* Google Cast Supported Media [cast-media] (encrypted protocols require a Custom Receiver); AudioSync design.
- **C6** Device authentication (C30, C31) is out of scope beyond what those clauses say. The sender never presents, forges, replays or works around Google-signed device credentials. *Source:* AudioSync design.
- **C7** A failure in the Cast session never stops the audio input, local speakers or AirPlay sessions of the same stream. *Source:* AudioSync design.
- **C8** The call through which the host hands audio to the sender MUST NOT allocate, lock, block, log or touch the file system. It copies frames into a preallocated single-producer, single-consumer ring and returns. Encoding, TLS and HTTP work run on the sender's own threads. *Source:* AudioSync design (the app's rule for audio callbacks).
- **C9** Every identifier the sender creates (request ids, stream URL tokens) is random or counter-based. The sender never sends a hardware address, serial number, host name or user name to the device. *Source:* AudioSync design.

## 2. Discovery

- **C10** The sender browses for `_googlecast._tcp` in the `local.` domain over multicast DNS, following PTR records to SRV, TXT and address records. *Source:* RFC 6762; RFC 6763; community protocol write-up [oakbits]; observed behavior of open-source senders [pychromecast].
- **C11** Instances under a subtype (names ending in `_sub._googlecast._tcp.local.`) are not devices and are ignored. *Source:* observed behavior of open-source senders [pychromecast]; RFC 6763 §7.1 (subtypes).
- **C12** Each TXT string is `key=value`; a string without `=` is skipped. Values are UTF-8 bytes as received. Tools that print DNS presentation format show non-ASCII bytes as a backslash and three decimal digits, and one open-source sender undoes that escaping in `fn` and `md` because its mDNS library leaves it in; the sender reads the raw record bytes, so the escaping never reaches it. Unknown keys are kept for diagnostics and otherwise ignored. *Source:* RFC 6763 §6; observed behavior of open-source senders [go-chromecast].
- **C13** TXT keys the sender reads:
  - `id`: the device's unique identifier, a UUID written as hex digits. An instance whose `id` is missing or does not parse as a UUID is skipped; one open-source sender does this to drop broken third-party emulators. The identifier is the device's key in the host's device list and settings.
  - `fn`: the friendly name the user set; it is the name shown in the host.
  - `md`: the model name, such as Chromecast or Chromecast Audio; shown as secondary text. A missing `md` is shown as an unknown model, never as an error.
  - `ve`: a protocol version identifier; the write-up lists 02 for the first Chromecast, 04 for Nexus Player and 05 for Chromecast Audio. Recorded for diagnostics only.
  - `ic`: a path on the device to its icon, such as `/setup/icon.png`. Not fetched by this version.
  - `ca`: sources disagree. One write-up calls it a certificate authority identifier (4100 on the first Chromecast, 5 on later devices); other readers treat it as a capability bit set, and Google's Open Screen library reads it as one (C89). The sender MUST NOT gate any behavior on `ca`.
  - `st`: Google's Open Screen library reads it as the receiver's status, 0 for idle and 1 for busy with an activity a sender may join. Recorded for diagnostics only.
  - `rs`, `bs`, `cd`, `rm`, `nf`: seen in the wild; no source used here gives their meaning. Not interpreted.

  *Source:* community protocol write-up [oakbits]; observed behavior of open-source senders [pychromecast], [go-chromecast]; Google Open Screen library [openscreen-receiver-info] (`ca` and `st`). G3 tracks `ca` and the uninterpreted keys.
- **C14** An instance whose SRV port is not 8009 is a Cast group, not a single device. It is listed as a group; C3 and C93 say how it is driven. The port is the only test the sender applies: no source ties a TXT value to groups firmly enough to rely on (C89). *Source:* observed behavior of open-source senders [pychromecast] (a port other than 8009 marks a group, and nothing else does). G1 confirms the port alone tells a group apart.
- **C15** The sender connects to the address and port from the SRV and address records, never to a port it assumes. Single devices announce port 8009. *Source:* community protocol write-up [oakbits] (port 8009, announced in DNS-SD); RFC 6763 §5.
- **C16** A device seen on several interfaces, or with both IPv4 and IPv6 addresses, is one device keyed by `id`. *Source:* AudioSync design. *Required:* the sender tries IPv4 addresses first, then IPv6, and remembers the address that worked.
- **C17** A device whose records expire (goodbye packet or TTL) is marked offline but kept in the list while a session with it is open; the session's own health (C36) decides whether it ends. *Source:* RFC 6762 §10.1 (goodbye packets); AudioSync design.
- **C18** The host MAY let the user add a device by address when multicast DNS is blocked. Such a device has no TXT data; it is keyed by address until a later browse finds its `id`. When that browse finds it, the offset (C77) stored under the address moves to the `id` if the `id` has none (0 ms counts as none); an offset the `id` already has wins. *Source:* observed behavior of open-source senders [pychromecast] (known addresses can be passed when discovery can't work; multicast DNS needs UDP port 5353 open); AudioSync design.
- **C89** A group is announced as an instance of its own: its own `id` (a UUID that is not any member's), its own `fn` (the group name set in the Google Home app), and an SRV record whose port is the group's port, not 8009, and whose target is the member that currently leads the group. Three sources hint at a TXT marker, and none settles one: Google's Android sender library defines a device capability `CAPABILITY_MULTIZONE_GROUP` with value 32 for a device that "represents a multi-zone group"; Google's Open Screen library reads `ca` as a capability bit field with bits for video out, video in, audio out, audio in and developer mode (values 1 to 16) and defines no group bit; and one open-source sender's model table maps the model name `Google Cast Group` to a group. No source says that a group's `ca` carries 32 or that its `md` reads `Google Cast Group`, so the sender tests the port alone (C14) and records every group's `ca` and `md` in the debug log. *Source:* observed behavior of open-source senders [pychromecast] (groups classed by port; a group's leader and UUID listed apart from the member's own); Google Cast Android sender reference [cast-android-device]; Google Open Screen library [openscreen-receiver-info]; AudioSync design. G1 records what groups announce.
- **C90** A group's records follow its leader. When the leader changes, the group's SRV target and address records move to another member while its `id` stays; the entry keeps its `id` and takes the new target, port and addresses. For a group the sender does not reuse the address remembered under C16: every connect and reconnect to a group resolves its records afresh and uses what they say then. A group whose records expire is marked offline as C17 says. *Source:* observed behavior of open-source senders [pychromecast] (every reconnect resolves the service again, which covers a leader handover); AudioSync design.
- **C91** Google's apps can also form a temporary group for one playback, when the user adds speakers to what is playing. Open-source senders see such a group as a discoverable service and say its port is missing from the list of saved groups that a device's setup interface returns. From multicast DNS alone a temporary group looks like a saved one, so the sender lists every group instance it finds; a temporary group leaves the list when its records expire (C17). *Source:* observed behavior of open-source senders [pychromecast] (dynamic groups; a multizone message that marks a temporary group being formed), [home-assistant-cast] (dynamic groups connected to as services and not shown as players); AudioSync design. G1 checks whether a temporary group is announced and plays.
- **C92** The sender never asks a device's HTTP setup interface (ports 8008 and 8443) for groups, leaders, members or capabilities. Google does not document that interface, and the Cast channel carries what the sender needs (C94). *Source:* AudioSync design; observed behavior of open-source senders [pychromecast] (it reads group lists and leaders from that interface).
- **C106** The host applies at most 256 discovery events per UI tick; the rest wait for the next tick, so a flood of multicast DNS answers cannot stall the UI thread. *Source:* AudioSync design.

## 3. Connection

- **C19** The sender opens one TCP connection to the device (C15) and runs TLS over it as the client. The connection stays open for the whole session; every Cast message in both directions travels on it. *Source:* community protocol write-ups [oakbits], [node-castv2]; RFC 8446 and RFC 5246 (TLS).
- **C20** Devices differ in the cipher suites they offer. The write-up lists ECDHE-RSA-AES128-GCM-SHA256 for the first Chromecast, ECDHE-RSA-AES256-GCM-SHA384 for Nexus Player and ECDHE-RSA-AES256-SHA (a CBC suite) for Chromecast Audio. The sender's TLS configuration MUST allow TLS 1.2 with ECDHE-RSA key exchange and AES-GCM suites, SHOULD also allow the AES-CBC-SHA suites so that older devices connect, and MAY offer TLS 1.3 as well. *Source:* community protocol write-up [oakbits] (2016; derived from the one suite each device negotiated with one client, not a list of what devices accept; devices may have changed since). G4 records which suites devices accept today. *Required:* a connection that fails the handshake is reported with the TLS alert it got (C80), so a device with another suite or protocol version shows up in the log; G4 tracks what older devices accept.
- **C21** The device's TLS certificate is not issued for a host name and does not chain to a public certificate authority. The sender MUST NOT verify the chain or the host name, and MUST NOT fail the connection because of the certificate. It records the certificate's SHA-256 fingerprint per device `id` for diagnostics only; a changed fingerprint is logged and never blocks. *Source:* observed behavior of open-source senders [pychromecast] (TLS client with host name checking and certificate verification both off); AudioSync design. G4 tracks how often devices change certificates.
- **C22** The channel is therefore encrypted but not authenticated: another host on the network could pose as the device. The sender sends nothing over it that is secret beyond the session's stream URL (C57), which is worth one session of audio and dies with it. *Source:* derived from C21; AudioSync design.
- **C23** Each message on the channel is a 4-byte unsigned big-endian length followed by that many bytes of one serialized `CastMessage`. The length counts only the message bytes, not itself. Reads assemble a whole message before parsing; a message can arrive split across TLS records or several can arrive in one. *Source:* community protocol write-ups [node-castv2], [oakbits]; observed behavior of open-source senders [pychromecast].
- **C24** `CastMessage` is a Protocol Buffers (proto2) message with these fields:
  - 1 `protocol_version`, enum, required; its only value is `CASTV2_1_0` = 0.
  - 2 `source_id`, string, required.
  - 3 `destination_id`, string, required.
  - 4 `namespace`, string, required.
  - 5 `payload_type`, enum, required; `STRING` = 0 or `BINARY` = 1.
  - 6 `payload_utf8`, string, optional; set when `payload_type` is `STRING`.
  - 7 `payload_binary`, bytes, optional; set when `payload_type` is `BINARY`.

  Exactly one of fields 6 and 7 is set, as `payload_type` says. The sender encodes and decodes this with the standard Protocol Buffers wire format, using an established crate. *Source:* community protocol write-up [node-castv2] and the Chromium protocol definition [chromium-cast-channel] (the message layout and field numbers, from the Chromium protocol definition); Protocol Buffers encoding documentation [protobuf-encoding].
- **C25** Google documents a 64 KB cap on transport messages. The sender never sends a larger message, and treats an inbound length prefix above 65 536 bytes, or a message that fails to parse, as a protocol fault that closes the channel (C81). The device is reported to close the connection itself when it can't parse what it got. *Source:* Google Cast media messages [cast-messages] (64 KB cap); community protocol write-up [oakbits] (the receiver closes the connection on a parse failure); AudioSync design.
- **C26** Endpoints are named by `source_id` and `destination_id`. The device platform is `receiver-0`; a running app is addressed by its `transportId` (C42); a destination of `*` is a broadcast to every sender connected to that endpoint. The sender uses `sender-0` as its own id in every message it sends. It accepts an inbound message only when its destination is `sender-0` or `*`, and drops any other. *Source:* community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast] (`sender-0` for all traffic). G13 tracks whether a per-session sender id is ever needed.
- **C27** The namespaces the sender uses: `urn:x-cast:com.google.cast.tp.connection` (virtual connections, C32), `urn:x-cast:com.google.cast.tp.heartbeat` (keep-alive, C34 to C36), `urn:x-cast:com.google.cast.receiver` (platform status, apps and device volume, C37 to C44 and section 6) and `urn:x-cast:com.google.cast.media` (playback, section 5). Messages on any other namespace are dropped, except as C31 says for `urn:x-cast:com.google.cast.tp.deviceauth`. *Source:* community protocol write-up [node-castv2]; Google Cast media messages [cast-messages].
- **C28** Messages on those four namespaces use `payload_type` `STRING`, with one JSON object in `payload_utf8`. Every object has a string `type` that names the message. Unknown `type` values and unknown fields are ignored; a payload that isn't valid JSON drops that one message and is logged, without closing the channel. *Source:* community protocol write-up [node-castv2] (JSON in the UTF-8 field); RFC 8259; AudioSync design.
- **C29** Requests on the receiver and media namespaces carry an integer `requestId`. The sender starts at a random positive value per channel and adds one per request, never uses 0, and never reuses a value on that channel. The device echoes the `requestId` in its reply and in the status broadcast the request caused; spontaneous status updates carry 0. A request without a reply within its own timeout counts as failed. Connection and heartbeat messages carry no `requestId`. *Source:* Google Cast media messages [cast-messages]; community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast] (PONG without a request id).
- **C30** Device authentication runs on `urn:x-cast:com.google.cast.tp.deviceauth`: a sender that chooses to authenticate the device sends a challenge to `receiver-0` as a binary payload, and the device answers either with a response (a signature, the device certificate and the intermediate certificates that chain it to Google) or with an error (an internal error, or that the connection is not TLS). It lets a sender check that it talks to a genuine Cast device. *Source:* community protocol write-up [node-castv2]; [oakbits] (the messages are defined in the same protocol file as `CastMessage`).
- **C31** No source reports that a Cast device or the Default Media Receiver requires a sender to authenticate the device, or authenticates the sender in turn: the write-up calls the step optional from the sender's side, while official SDKs perform it. The sender in this version does not send the challenge and ignores any inbound message on the device authentication namespace. *Source:* community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast] (its connection code, as read, launches the Default Media Receiver without a device authentication step). G14 tracks a device that would refuse.

## 4. Session

- **C32** Before it sends anything else to an endpoint, the sender opens a virtual connection to it: a message of type `CONNECT` on the connection namespace, addressed to that endpoint. A virtual connection also subscribes the sender to that endpoint's broadcasts. A message of type `CLOSE` ends it, from either side; a device usually sends `CLOSE` after an error. *Source:* community protocol write-up [node-castv2].
- **C33** Right after the TLS handshake the sender sends `CONNECT` to `receiver-0`, then `GET_STATUS` on the receiver namespace to `receiver-0`. The session is ready for launch (C40) when the matching `RECEIVER_STATUS` arrives. *Source:* community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast] (status read before a launch). *Required:* no `RECEIVER_STATUS` within 5 s ends the attempt as a connect failure (C80).
- **C34** The sender sends a message of type `PING` on the heartbeat namespace to `receiver-0` at a fixed interval while the channel is open. The write-up gives a default of about 5 s; one open-source sender pings every 10 s. *Source:* community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast]. *Required:* every 5 s.
- **C35** The device also sends `PING` to the sender. The sender answers each with a message of type `PONG` on the heartbeat namespace, to the endpoint that sent the `PING`, promptly. A device ends the connection of a sender that stops answering. *Source:* community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast]. G12 tracks the device's own timeout.
- **C36** The channel is dead when nothing at all has arrived on it for a set time. One open-source sender resets the connection when no `PONG` has arrived for 20 s. *Source:* observed behavior of open-source senders [pychromecast]. *Required:* any inbound message resets the timer; 15 s without one (three ping intervals) closes the channel and starts recovery (C81).
- **C37** `RECEIVER_STATUS` carries a `status` object. The fields the sender reads: `volume.level` (0.0 to 1.0), `volume.muted`, `volume.controlType`, `volume.stepInterval`, and the `applications` list, each entry with `appId`, `displayName`, `sessionId`, `transportId`, `namespaces` (objects with a `name`) and `statusText`. A missing `level` reads as 1.0, a missing `muted` as false and a missing `controlType` as `attenuation`. Other fields (such as `isActiveInput` and `isStandBy`) are logged only. *Source:* community protocol write-up [node-castv2]; Google Cast sender reference [cast-volume]; observed behavior of open-source senders [pychromecast] (the defaults).
- **C38** The device broadcasts `RECEIVER_STATUS` on its own whenever its state changes, for example when another sender launches an app or someone changes the volume on the device or in another controller. The sender treats every `RECEIVER_STATUS`, solicited or not, as the current state. *Source:* community protocol write-up [node-castv2] (a virtual connection subscribes to status broadcasts); Google Cast media messages [cast-messages] (spontaneous updates carry `requestId` 0).
- **C39** The Default Media Receiver's app id is `CC1AD845`. It is Google-hosted, needs no registration, plays audio and video from a URL, and has no customizable interface. *Source:* community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast]; Google Cast Web Receiver overview [cast-receiver].
- **C40** The user starting a stream on a Cast device is consent to take it over. If the status already lists an app with `appId` `CC1AD845`, the sender reuses that app (C42) and its next `LOAD` replaces whatever it plays. Otherwise the sender launches the Default Media Receiver, which replaces any other running app. *Source:* observed behavior of open-source senders [pychromecast] (a launch is skipped when the app already runs); AudioSync design.
- **C41** A launch is a message of type `LAUNCH` with `appId` `CC1AD845` on the receiver namespace to `receiver-0`. It succeeds when a `RECEIVER_STATUS` lists that app with a `sessionId` and a `transportId`; it fails on a message of type `LAUNCH_ERROR`, which carries a `reason`. One open-source sender retries once when the reason is `CANCELLED`. *Source:* community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast]. *Required:* retry once on `CANCELLED`; no success within 15 s fails the launch. The 15 s are counted per `LAUNCH` sent, so the retry gets a fresh 15 s.
- **C42** The app's `transportId` is the destination for every message to the app. The sender sends `CONNECT` to it before any media message, which also subscribes it to the app's media status. It records the app's `sessionId` for C44 and C87. *Source:* community protocol write-up [node-castv2].
- **C43** A `RECEIVER_STATUS` whose `applications` no longer contains the app with the recorded `sessionId` means the app was stopped or replaced, by another sender, the device's own controls or the user. The session ends with the reason "taken over" and is not relaunched on its own. *Source:* observed behavior of open-source senders [go-chromecast] (a status naming a different app ends playback); AudioSync design.
- **C44** A message of type `STOP` with the recorded `sessionId` on the receiver namespace to `receiver-0` stops the app. *Source:* community protocol write-up [node-castv2]; observed behavior of open-source senders [pychromecast].

### Groups

- **C93** A group session runs over one channel to the group's own address and port (C15, C90), and sections 3 to 8 apply to it unchanged: TLS with any certificate, `CONNECT` and `GET_STATUS` to `receiver-0`, the heartbeat, the launch of the Default Media Receiver, `LOAD`, volume and teardown. The device at the other end of the channel is the leader. The sender opens no channel to any member during a group session. Open-source senders drive a group with the same client, the same platform and media handling and the same Default Media Receiver as a single device, taking the port from discovery because a group's port differs; Google's group FAQ says playback reaches "all speakers in the original format" and that a group can be cast to from Chrome. *Source:* observed behavior of open-source senders [pychromecast], [home-assistant-cast]; Google support FAQ [google-group-faq]; AudioSync design. G1 confirms that this sender's live stream plays on every member.
- **C94** After the first `RECEIVER_STATUS` of a group session (C33), the sender sends `GET_STATUS` on the namespace `urn:x-cast:com.google.cast.multizone` to `receiver-0`. The reply, `MULTIZONE_STATUS`, carries `status.devices`, a list of members, each with `deviceId` and `name`; the sender keeps it as the group's member list and hands it to the host. Changes arrive unasked on the same namespace: `DEVICE_ADDED` and `DEVICE_UPDATED` carry a `device` object with `deviceId` and `name` and add or refresh one member, `DEVICE_REMOVED` carries a `deviceId` and removes it, and a later `MULTIZONE_STATUS` replaces the whole list. Other fields are logged only. *Source:* observed behavior of open-source senders [pychromecast] (the namespace on the group's platform endpoint, these message types and the fields read from them); AudioSync design. *Required:* no `MULTIZONE_STATUS` within 5 s is not an error; the session plays on with the member list unknown and the host shows the group without members. G1 records the full messages.
- **C95** A member's `deviceId` is matched against the `id` of the single devices the host has discovered, both read as UUIDs so that case and dashes don't matter. One open-source sender matches them as strings in the lowercase dashed UUID form of a device's own identifier, so the two name the same device there. A member with no discovered match is shown by its `name` alone. *Source:* observed behavior of open-source senders [pychromecast]; AudioSync design. G1 confirms the match.
- **C96** The multizone namespace has other message types. `PLAYBACK_SESSION_UPDATED`, which one open-source sender reads as a temporary group being formed, and `CASTING_GROUPS`, the reply to a `GET_CASTING_GROUPS` request, are logged and change nothing. The sender sends no multizone request other than `GET_STATUS`, and logs each unknown type once per session. *Source:* observed behavior of open-source senders [pychromecast]; AudioSync design.
- **C97** No message announces a leader change. A handover shows up as the channel closing or going silent (C36) and the group's records moving (C90). The sender recovers as C81, against the freshly resolved address; when the new leader's status does not list the app with the recorded `sessionId`, the sender relaunches and loads as at the start. *Source:* observed behavior of open-source senders [pychromecast] (a leader handover is followed by resolving the service again on reconnect; no message reports it); derived from C81; AudioSync design. G1 records what a handover does to a playing session.
- **C98** Membership can change during a session. Google's FAQ says speakers can be added to a playing group, and that removing speakers from an active group, or editing or deleting a group that is casting, stops playback. A stop arrives as `IDLE` or as the app leaving the status, and the sender handles it as C43 and C86: taken over, no relaunch. An added member changes only the member list (C94). *Source:* Google support FAQ [google-group-faq]; Google Nest Help [google-speaker-groups] (edits to a casting group stop it); AudioSync design. G1 checks what a member going offline does.
- **C99** A member of a group stays a target of its own. Google's FAQ says that casting to a single speaker of a group during group playback stops group playback on all speakers. This clause covers a cast to a member of a playing group by a sender other than the one playing the group; within its own stream, C2 refuses a member of the group it is playing. A session this sender starts on a member ends any group playback by another sender that includes the member (the user's start is consent, C40), and a group session of this sender ends as taken over (C43, C86) when another sender casts to one of its members. Google's FAQ says a speaker can belong to many groups, while Google Assistant Help lists eight models that the Google Home app keeps to one group; the sender assumes neither and lists each group under its own `id`. *Source:* Google support FAQ [google-group-faq]; Google Assistant Help [google-assistant-groups]; derived; AudioSync design.

## 5. Media

### Loading the stream

- **C45** Playback messages use the media namespace `urn:x-cast:com.google.cast.media`, sent to the app's `transportId` after the virtual connection of C42. *Source:* Google Cast media messages [cast-messages]; community protocol write-up [node-castv2].
- **C46** The sender starts playback with one message of type `LOAD` carrying `requestId`, `autoplay` true and a `media` object with `contentId` (the stream URL, C55 to C57), `contentType` (the MIME type of C63), `streamType` (C48), `duration` -1 and `metadata` (C53). It sends no `currentTime`. *Source:* Google Cast media messages [cast-messages] (the `LOAD` fields; `autoplay` defaults to true); Google Cast receiver reference [cast-mediainfo] (`duration` is -1 for a live stream).
- **C47** `contentId` is at most 1 KB, so the stream URL stays short. Newer receiver documentation adds an optional `contentUrl` that, when present, is used as the media URL instead of `contentId`; the sender leaves it out and puts the URL in `contentId`, which every version described treats as the media URL. *Source:* Google Cast media messages [cast-messages] (`contentId` up to 1 KB, usually a URL); Google Cast receiver reference [cast-mediainfo] (`contentUrl`). G13 tracks devices that would need `contentUrl`.
- **C48** `streamType` is `LIVE`. The documented values are `NONE`, `BUFFERED` and `LIVE`; one open-source sender defaults to `LIVE` and documents that live content loaded without a position starts at the live position, another sends `BUFFERED` for files. One project's maintainer blamed delay spikes of many seconds on a stream type that wasn't set correctly. *Source:* Google Cast media messages [cast-messages]; observed behavior of open-source senders [pychromecast], [go-chromecast]; user reports [mkchromecast-61]. G9 tracks what the choice changes inside the receiver.
- **C49** After `LOAD`, the app answers with `MEDIA_STATUS`, whose `playerState` goes through `BUFFERING` to `PLAYING`, or with an error (C83). A second `LOAD` sent before the first finished cancels the first with `LOAD_CANCELLED`, so the sender never has two `LOAD` requests outstanding on one session. *Source:* Google Cast media messages [cast-messages]. *Required:* no `PLAYING` within 20 s of the `LOAD` reply ends the attempt as a load failure (C83).
- **C50** The sender records the `mediaSessionId` from the `MEDIA_STATUS` that answers its `LOAD` and uses it for every later media request. `STOP` invalidates it. *Source:* Google Cast media messages [cast-messages].
- **C51** `MEDIA_STATUS` also arrives on its own whenever the player changes. `playerState` is one of `IDLE`, `PLAYING`, `BUFFERING` and `PAUSED`; with `IDLE`, an `idleReason` of `CANCELLED`, `INTERRUPTED`, `FINISHED` or `ERROR` may say why. Section 8 says what each means for the session. A `BUFFERING` after `PLAYING` means the receiver ran dry; the sender counts it (C79). *Source:* Google Cast media messages [cast-messages]; AudioSync design.
- **C52** The sender never sends `PAUSE`, `PLAY` or `SEEK` in this version. When the host's audio pauses or the input is silent, the stream keeps running and carries silence, so the receiver's buffer and the latency stay as they were. *Source:* AudioSync design; derived from section 7 (a paused receiver with a live input would come back later than before). One user report found that an explicit `PLAY` after `LOAD` shortened the start; G9 covers it.
- **C53** `metadata` uses `metadataType` 3 (music track) with any of `title`, `artist`, `albumName` and `images`, a list of objects each with a `url`. Every field but `metadataType` is optional, and the sender leaves out what the host doesn't know instead of sending placeholders. An artwork image is served by the stream server (C57) under its own random path, at most 1280 by 720 pixels. *Source:* Google Cast media messages [cast-messages]; Google Cast Supported Media [cast-media] (images are limited to 720p and should be 1280x720 or less).
- **C54** The sources describe no way to change the metadata of a loaded live item on the Default Media Receiver without a new `LOAD`, and a new `LOAD` restarts the fetch and the receiver's buffer. The sender sends metadata with the `LOAD` only; a track change in the host does not reload. *Source:* Google Cast media messages [cast-messages]; derived. G10 tracks a way to update it.

### Serving the audio

- **C55** The device fetches the stream itself, from the URL in `contentId`. The URL's host is a literal IP address: the local address of the sender's TCP connection to that device (C19), which is an address the device can route back to. IPv6 addresses go in brackets. Host names and `.local` names are never used. *Source:* observed behavior of open-source senders [catt] (it picks the local address on the device's subnet) and [go-chromecast] (an HTTP server on the host that the device fetches from); RFC 3986 §3.2.2; AudioSync design.
- **C56** The stream server listens on that one address only, on a port the operating system assigns, and only while a session needs it. A host firewall can block the device's fetch; one open-source sender tells its users to open a port range for this. When no fetch arrives (C85) the host says that the device could not reach this computer and names the firewall as a likely cause. *Source:* observed behavior of open-source senders [catt] (TCP ports 45000 to 47000 must be allowed); AudioSync design.
- **C57** The URL path holds a random token of at least 128 bits, new for each session. Requests for any other path get 404. The token stops working when the session ends. *Source:* AudioSync design.
- **C58** The stream server answers only requests whose source address is one of the session device's known addresses (C16); others get 403. *Source:* AudioSync design.
- **C59** A `GET` for the stream gets HTTP/1.1 `200` with `Content-Type` equal to the `contentType` of the `LOAD`, `Cache-Control: no-store`, `Access-Control-Allow-Origin: *`, no `Content-Length`, and a body in the chunked transfer coding that runs until the session ends. A `HEAD` gets the same headers and no body. Google requires CORS headers only for adaptive streaming and subtitles; one open-source sender sends the header on every file it serves, and it costs nothing. *Source:* RFC 9110; RFC 9112 §7.1 (chunked); Google Cast Supported Media [cast-media] (CORS); observed behavior of open-source senders [catt]. G6 tracks whether every device accepts chunked bodies.
- **C60** A live stream has no fixed byte positions. The stream server ignores any `Range` header and answers as in C59, which HTTP allows. *Source:* RFC 9110 §14.2 (a server MAY ignore Range); AudioSync design. G6 covers devices that insist on `206`.
- **C61** Each `GET` starts at the live edge, with a fresh stream header (C63). A session has one stream response at a time: a new `GET` from the device ends the older response. The device closing the connection (reset or broken pipe) is normal and is not logged as an error. *Source:* observed behavior of open-source senders [catt] (connection resets and broken pipes from the device are expected and ignored); AudioSync design.
- **C103** No source says which device of a group fetches the stream URL: the leader alone, every member, or a new leader after a handover. For a group session the stream server therefore widens C58 and C61. It answers requests from the group's current addresses (C90) and from the addresses of every discovered device whose `id` matches a member (C95), read at each request; others still get 403, an old leader the records stopped listing included, even before the sender reconnects (C97). It keeps one stream response per source address, so a new `GET` ends only the older response from the same address, and it holds at most one response per known member plus one. C85 holds as written: the first fetch from any accepted address counts. *Source:* AudioSync design; Google support FAQ [google-group-faq] (every speaker plays the original format, without saying how the audio reaches it). G1 settles who fetches.

### Formats

- **C62** For audio, Google lists the codecs HE-AAC, LC-AAC, MP3, Opus, Vorbis, WAV (LPCM), WebM and FLAC (FLAC up to 96 kHz and 24 bits), and the containers MP2T, MP3, MP4, OGG, WAV and WebM. Progressive download without adaptive switching is a supported protocol. *Source:* Google Cast Supported Media [cast-media].
- **C63** The sender streams one of two formats, chosen per session:
  - WAV with 16-bit LPCM, two channels, at the stream's sample rate (44 100 or 48 000 Hz), `contentType` `audio/wav`. The RIFF and data chunk sizes are unknown for a live stream and are set to their largest value. The rate is 1 411 200 bit/s at 44 100 Hz and 1 536 000 bit/s at 48 000 Hz, and a 32-bit data size covers about 6 h 45 min and 6 h 12 min of audio at those rates.
  - FLAC in its native stream format, same channels and rates, `contentType` `audio/flac`, with the STREAMINFO total sample count set to 0 (unknown), encoded by an established encoder.

  WAV is the first choice: it adds no encoder delay and needs no codec. FLAC is the fallback (C84). Lossy codecs are not used in this version; one project's documentation reports up to 8 s of delay with MP3 on one setup, and a user there found WAV started faster than MP3 or Ogg. *Source:* Google Cast Supported Media [cast-media]; RFC 9639 (FLAC, STREAMINFO); derived (rates and durations from the sample format); user reports [mkchromecast], [mkchromecast-61]; AudioSync design. G5 tracks how devices treat the WAV size fields and long runs.
- **C64** The stream server writes audio as it arrives from the ring, in blocks of 20 ms, never faster than real time, and never sends a backlog: a new response begins with the newest audio. A send that would block (the device not reading) leaves frames in a per-session queue capped at 2 s; on overflow the oldest frames are dropped and the event is counted (C79). *Source:* AudioSync design; derived from section 7 (audio queued in front of the receiver is latency).

## 6. Volume and mute

- **C65** Device volume is set with a message of type `SET_VOLUME` on the receiver namespace to `receiver-0`, carrying a `volume` object with either `level` (0.0 to 1.0) or `muted` (true or false); level and mute are separate messages. Mute is independent of level. *Source:* observed behavior of open-source senders [pychromecast]; community protocol write-up [node-castv2]; Google Cast sender reference [cast-volume] (`level` 0.0 to 1.0, where 1.0 is the device's maximum; `muted` independent of level).
- **C66** The media namespace also has a `VOLUME` message, but it sets the stream's own volume, meant for effects such as fades, and must not drive the device's volume control. The sender never uses it. *Source:* Google Cast media messages [cast-messages].
- **C67** The sender clamps a requested level to 0.0 to 1.0 before sending. *Source:* observed behavior of open-source senders [pychromecast] (clamps), [go-chromecast] (rejects values outside the range); AudioSync design.
- **C68** `volume.controlType` says what can be changed: `attenuation` (the device's own volume can be changed), `fixed` (the device's volume is locked) or `master` (the volume of a TV or audio device is changed through master system control). With `fixed`, the host shows the volume control as unavailable and the sender sends no `SET_VOLUME`. *Source:* Google Cast sender reference [cast-namespace].
- **C69** `volume.stepInterval` is the device's volume step. The host's step-up and step-down actions move the level by that amount; the host's slider sends its value as is, and the shown level is always the one the latest `RECEIVER_STATUS` reports. Without a reported step, each host keeps the step its other volume sliders use (1 on Windows, 5% on the Mac). Windows rounds a reported step to a whole level, at least 1, since its slider moves in whole levels. *Source:* Google Cast sender reference [cast-volume] ("the allowed steps for changing volume"); AudioSync design. G11 tracks whether devices round other values to the step.
- **C70** Volume changed elsewhere (the device's buttons, a remote, another app) arrives as `RECEIVER_STATUS` (C38); the host moves its control to the reported level and does not send its own value back. While the user drags the host's slider, the sender sends at most one `SET_VOLUME` every 100 ms, the latest value winning. *Source:* AudioSync design.
- **C71** The sender never scales samples for volume: device volume stays on the device. *Source:* AudioSync design.
- **C100** A group has one volume control and one mute in the host, bound to the `volume` of the group's own `RECEIVER_STATUS` and driven by `SET_VOLUME` to the group's `receiver-0`, exactly as C65 to C70 say for a device; `fixed` hides the control as in C68. What a group does with that level is not documented: Google's help tells users to set the speakers of a group one by one, and says a smart display's slider changes "an individual speaker or all of the speakers". The host shows only what the group reports after a change and never assumes the change reached every member. It sends no volume to a member during a group session; each member's own level stays with the member's controls and the Google Home app. *Source:* Google support pages [google-cast-group-volume], [google-assistant-groups]; Google Cast sender reference [cast-volume]; AudioSync design. G1 records what a group level does to the members.
- **C104** The host's master volume and the device's zone volume (S249 in `docs/ENGINE_SPEC.md`) scale a Cast device or group the way they scale AudioSync's own AirPlay speakers (their sender gets each speaker's volume times its zone's and the master) and local outputs (S71), but on the device's volume, never on the samples (C71). The host keeps the user's own level for the device, s (0.0 to 1.0, what its slider shows), and with the master m and the zone z (both 0.0 to 1.0, z being 1.0 outside a zone) the level it sends in `SET_VOLUME` (C65) is m × z × s, clamped as C67 says: a master or zone of 0 sends level 0, never `muted`, so the device's mute stays the user's own. A slider change sends m × z × s, and a step action (C69) moves s by the step and, with m × z below 1, sends m × z × s as a level; a master or zone change sends m × z × s at once to the device or group in a session. The C70 interval paces these, and nothing else throttles them. A level equal to the device's current report is sent but not awaited, since no status will answer it. A reported level that answers none of the levels the host sent (C70: the device's buttons, another controller) moves s to level ÷ (m × z), clamped to 0.0 to 1.0; with m × z at 0, s stays as it is (S250). The first status of a session is the exception (C105); later changes from elsewhere are never sent back (C70). A `fixed` volume sends nothing (C68). *Source:* AudioSync design.
- **C105** At the start of a session the host sets the device or group to m × z × s (C104), louder or quieter than it reports, so it plays what the sliders show; the level goes as soon as the session's first status gives the volume, and only when that status's level does not already answer m × z × s. That first status is never read back as a change of s. A device without an own level yet (none set or read in this run) takes the first status's level ÷ (m × z) as s, clamped to 0.0 to 1.0, or the level itself with m × z at 0, so a device turned on for the first time keeps its loudness when the master and its zone allow it. A `fixed` volume is not set (C68). *Source:* AudioSync design.

## 7. Timing and latency

- **C72** What the sender controls: when each byte leaves it, the format and so the encoder delay (none for WAV), and how much audio waits in its own queue (C64). What it does not control: how much the receiver buffers before it reports `PLAYING`, the size of the receiver's buffer while playing, the receiver's output clock, the delay of whatever the device feeds (a TV, a soundbar, an amplifier), and the network. The Default Media Receiver offers no message to set its buffering; a custom receiver could, and is out of scope (C4). *Source:* Google Cast media messages [cast-messages] (no buffering field in any message); Google Cast Web Receiver overview [cast-receiver] (the Default Media Receiver cannot be customized); derived.
- **C73** Nothing in the Cast media protocol ties a sample to a time on a shared clock: there is no sender clock, no presentation timestamp and no clock exchange. The only position report is `MEDIA_STATUS.currentTime`, in seconds. A Cast device therefore cannot be told to play a frame at a given moment, and the sender never claims sample-accurate sync for it. *Source:* Google Cast media messages [cast-messages] (the full field lists of `LOAD` and `MEDIA_STATUS`); derived.
- **C74** Google documents no startup or steady latency for the Default Media Receiver. User reports for live audio over HTTP spread widely: under 2 s, about 3 s with WAV, about 20 s on one smart display and over 30 s with MP3 in one thread; 1 to 2 s in some cases and about 13 s as a common case in another; up to 8 s with one MP3 setup in a project's documentation. The latency is of the order of seconds, differs by device, format and sender behavior, and can differ from one run to the next. *Source:* user reports [mkchromecast-61], [gnd-359]; project documentation [mkchromecast]; derived.
- **C75** The latency can also grow during a run: one report says data buffered during setup is never drained, another that the delay increases over time. A receiver whose output clock runs slower than the host's capture clock takes audio more slowly than it arrives, so audio piles up in front of it; one that runs faster drains its buffer and stalls (`BUFFERING`, C51). *Source:* user reports [gnd-359], [mkchromecast-61]; derived.
- **C76** Google keeps its own Cast groups in step inside its devices. The only user-facing control is a per-device group delay correction in the Google Home app, which affects group playback only and does nothing when casting to a single device; Google lists typical inherent delays of 0 to 40 ms for speakers, 0 to 80 ms for soundbars and 0 to 70 ms for receivers. No source describes a sender message that reaches this mechanism, so a third-party sender can't use it. *Source:* Google support page [google-group-delay]; derived.
- **C77** Cast is therefore a measured-offset output, not a synchronized one. The host keeps local speakers and AirPlay receivers in step with a Cast device only by delaying them by that device's measured latency, through its per-speaker delay control, and says in its interface that a Cast device is kept in step approximately. Local outputs never wait for the Cast device to start; the Cast device joins when it joins. The offset is stored per device `id` and reused on the next session as a starting point, to be checked again. *Source:* AudioSync design; derived from C72 to C76. *Required:* no automatic correction from `currentTime` or queue state in this version; G7 and G8 decide whether one can be added.
- **C77a** When the host must know how long audio already sent to a Cast device still plays, and the device has no stored offset (none, or 0 ms), it takes a starting guess by the format the session plays: 3000 ms for WAV, 6000 ms for FLAC and while no format is reported yet, on top of any time the host holds the Cast feed back. A stored offset replaces the guess. The guess only sets how long the host waits for that audio to play out, as Calibrate All does before its first sweep; it is never applied as a delay to other outputs (C77), and a lossy format is never used for a device that plays in step with other outputs (C63). *Source:* user reports [mkchromecast-61] and [cdas] (live WAV 2 to 5 s; MP3 and AAC 8 to 35 s); the FLAC figure is derived, not measured: the reports in [cdas] start later as the byte rate falls, and FLAC has about half of WAV's byte rate; AudioSync design. *Required:* G7 replaces both guesses with measured figures.
- **C78** The sender reports its view of the session to the host's debug log once per second while playing: audio duration sent since the `LOAD`, frames waiting in its queue, the latest `currentTime` and `playerState`, the counts of C79, and the silent frames sent since the `LOAD` because the input ran dry (C52). The Mac's line shows those silent frames as the change since that attempt's previous line. These are diagnostics; the host does not drive delays from them. *Source:* AudioSync design. G8 tracks whether `currentTime` tracks what is heard.
- **C79** The sender counts drift events: frames dropped on queue overflow (C64), frames the full ring drops or refuses, and `BUFFERING` after `PLAYING` (C51). When the drift since the `LOAD` adds up to more than 250 ms of audio, the host MAY restart the stream (a new `LOAD` on the same app) to bring the latency back to its starting value, accepting a short gap; it tells the user when it does. Until G7 gives drift rates the restart is only a user action (a Resync control that sends a new `LOAD`), never an automatic trigger, because a restart costs a gap of seconds and can land at a different latency (C74). *Source:* AudioSync design; derived from C74 and C75. G7 tracks the drift rates real devices show.
- **C101** A group is a measured-offset target, as C77 says for a device: one offset from the host to what the group plays, stored under the group's `id` and never under a member's, and reused as the starting point of the next session. Keeping the members in step with each other is the group's own work (C76). The per-device group delay correction in the Google Home app shifts members against each other and so can shift what the host measures; a stored group offset is checked again after such a change. *Source:* Google support page [google-group-delay] (the correction applies to group playback only); derived from C76 and C77; AudioSync design.
- **C102** No source gives what a group adds to a single device's startup or steady latency, or how far apart its members drift over a long live stream. The host never derives a group's offset from its members' offsets, and never applies a member's stored offset to the group or the group's to a member. *Source:* Google support page [google-group-delay] (correction figures of tens of milliseconds, nothing on group latency); derived; AudioSync design. G1 measures both.

## 8. Errors and teardown

- **C80** A connect failure (no TCP connection, a TLS handshake error, or no `RECEIVER_STATUS` in time, C33) is reported with its cause. While the user keeps the device selected, the sender retries after 1 s, doubling the wait up to 30 s. One open-source sender starts at 5 s and doubles up to 300 s. *Source:* observed behavior of open-source senders [pychromecast]; AudioSync design.
- **C81** When the channel dies (C36), closes, or hits a protocol fault (C25), the sender reconnects once at once. If the status then still lists the Default Media Receiver with the recorded `sessionId`, it sends `CONNECT` to the `transportId` and `GET_STATUS` on the media namespace and carries on; the device's HTTP fetch continues or restarts on its own (C61). Otherwise it relaunches and loads as at the start. When the media `GET_STATUS` gets an empty `status` list or no answer in time, the media ended during the outage, and the sender sends one new `LOAD`; if that fails, the session ends with its reason. A failed reconnect falls back to C80. *Source:* AudioSync design; Google Cast media messages [cast-messages] (media `GET_STATUS`).
- **C82** A `CLOSE` from the app's `transportId` ends the app connection. The sender checks the platform status: if the app is gone, C43 applies; if it still runs, the sender reconnects the virtual connection once. A `CLOSE` from `receiver-0` is handled as C81. *Source:* community protocol write-up [node-castv2] (a receiver sends `CLOSE`, usually after an error); observed behavior of open-source senders [go-chromecast] (a `CLOSE` ends playback); AudioSync design.
- **C83** Error replies and what the host shows: `LAUNCH_ERROR` (its `reason`), `LOAD_FAILED` (the player is `IDLE`; any `detailedErrorCode` goes to the log), `LOAD_CANCELLED` (a fault in the sender, C49), `INVALID_PLAYER_STATE`, and `INVALID_REQUEST` with `reason` `INVALID_COMMAND` or `DUPLICATE_REQUESTID` (both faults in the sender, logged with the request). Each ends the attempt with a reason the user can read; none of them stops other outputs (C7). When the user's Resync (C79) fails on a live channel (`LOAD_FAILED`, no fetch as in C85, or no `PLAYING` in time), the sender reconnects as C81 once and sends a new `LOAD`; if that fails too, the session ends with its reason. A channel that dies during a Resync follows C81 as usual. *Source:* Google Cast media messages [cast-messages]; observed behavior of open-source senders [pychromecast] (`LAUNCH_ERROR` and its `reason`; `detailedErrorCode` on `LOAD_FAILED`).
- **C84** On `LOAD_FAILED`, or `IDLE` with `idleReason` `ERROR` before the first `PLAYING`, with WAV, the sender tries once more with FLAC (C63); a second failure ends the attempt. The format that worked is remembered per device `id` and tried first next time. *Source:* AudioSync design.
- **C85** If the device has not fetched the stream URL within 10 s of the `LOAD` reply, the attempt ends with the error of C56. *Source:* AudioSync design.
- **C86** While playing, `IDLE` with `INTERRUPTED` or `CANCELLED`, or a `MEDIA_STATUS` naming another `mediaSessionId` or content, means someone else replaced or stopped the stream: C43 applies, no reload. `IDLE` with `ERROR` is reported and handled as C81 once, then ends the session. `IDLE` with `FINISHED` happens only when the stream response ended; one the sender did not cause by ending the response is unrequested. The sender reloads after every unrequested `FINISHED`, rate-limited: a second unrequested `FINISHED` within 10 minutes of the previous one ends the session with its reason, as a failed reload does in C81, so a device that keeps finishing the stream cannot hold the sender in a reload loop. The rule reacts to the device and never reloads ahead of time: the sender cannot know a device's play limit, and a reload made early gaps the audio the same way. Observation, inferred and not measured: one session ended after about 12 h 24 min of play with an unrequested `FINISHED`; no limit is assumed from it. *Source:* Google Cast media messages [cast-messages]; observed behavior of open-source senders [go-chromecast] (`FINISHED` and `INTERRUPTED` treated as the end of playback); AudioSync observation (one long session); AudioSync design. *Required:* the window is a session setting with a default of 10 minutes, read against a clock the test can replace, so a fake-receiver test may use a fake clock or a shortened window. Two unrequested `FINISHED` 20 minutes apart (or two windows apart on a shortened window) each get a reload, two reload `LOAD` messages after the first `LOAD`, and the session stays up; two within one minute get one reload `LOAD` and then end the session with `FINISHED` as its reason.
- **C87** When the user stops the stream, the sender, in order: sends media `STOP` with the `mediaSessionId`; sends receiver `STOP` with the recorded `sessionId` if the status still lists the Default Media Receiver with that `sessionId`; sends `CLOSE` to the `transportId` and to `receiver-0`; closes TLS; ends the stream response and closes the listener. Each step waits at most 2 s for a reply, and a missing reply never blocks the next step. It never stops an app it did not launch or reuse. A stop while a launch still waits for its status sends no `STOP`, since no `sessionId` or `transportId` is known yet: only the `CLOSE` to `receiver-0` goes, and the app that launch starts is left running, its late status ignored. *Source:* Google Cast media messages [cast-messages] (media `STOP`); community protocol write-up [node-castv2] (`STOP`, `CLOSE`); AudioSync design.
- **C88** When the host quits, the sender runs C87 with 3 s in total, then drops whatever is left. A quit during a launch sends no `STOP`, since no `sessionId` is known yet: as in C87, only the `CLOSE` to `receiver-0` goes. A device left with a loaded app and no sender is harmless: the app goes idle when its fetch ends, and the device drops the dead channel (C35). *Source:* AudioSync design; community protocol write-up [node-castv2].

## 9. Gaps

What a sender needs that no source used here settles. Each gap names the clauses it touches and what would close it. Gaps marked *hardware* need a real Cast device.

- **G1 Cast groups** (C3, C14, C89 to C103). Settled from sources: a group is its own instance with its own `id` and a port other than 8009, led by one member; open-source senders drive it with the same channel protocol and the Default Media Receiver; members are listed on the multizone namespace; casting to a member or removing one stops group playback. Unknown, each needing a real group: (a) whether every group announces a port other than 8009 and every single device 8009, and what `ca`, `md` and `st` a group carries; (b) whether this sender's live WAV and FLAC streams play on every member through the group's port; (c) which addresses fetch the stream URL (C103); (d) the full `MULTIZONE_STATUS` and `DEVICE_*` messages, and whether `deviceId` equals the member's `id`; (e) what `SET_VOLUME` on the group does to each member's level, and what level the group reports; (f) what a leader handover and a member going offline do to a playing session; (g) whether a temporary group is announced and plays; (h) the group's startup latency next to a single member's, and how far its members drift apart over a run. Settle: *hardware*, two Cast speakers in one saved group. The debug log captures each group's TXT record (a), each fetch's source address and request header names (up to 24, the rest counted) with its User-Agent, Range and Icy-MetaData values (each up to 96 characters, the stream token never logged) at the stream server (c) and every multizone message (d). Steps: play to the group and listen at both speakers (b); move the group's level and read each member's level in the Google Home app (e); unplug the leader, then the other member, during playback (f); add a third speaker from the Google Home app's playback screen and play to the temporary group if it appears (g); measure the group and one member alone with G7's click train, ten starts each, then a 60-minute group run with a microphone between the speakers (h).
- **G2 Several Cast devices in one stream** (C2). Unknown: how far apart two devices fed the same stream play, and whether that spread holds over a run. Settle: *hardware*, two devices side by side, each with its own session, a click train recorded by one microphone; ten starts, 60 minutes each. Parked: Google's group delay setting applies to group playback only [google-group-delay], open-source senders drive each device as its own session and none documents keeping two in step [pychromecast], [go-chromecast], and no source measures the spread. Lifting C2 would be a new feature, while groups (G1) already put several devices in one stream with the devices' own sync.
- **G3 TXT keys** (C13, C89). Google's Open Screen library reads `ca` as a capability bit field and `st` as idle or busy, which favors the bit field reading of `ca`. Unknown: whether devices fill `ca` and `st` that way, whether a group sets the value 32 in `ca`, and what `rs`, `bs`, `cd`, `rm` and `nf` mean. Settle: TXT records captured from several models in several states (idle, playing, in a group), compared key by key; any Google documentation that names them.
- **G4 Receiver TLS** (C20, C21). Unknown: how long a device keeps its TLS certificate, whether it changes on reboot or on a schedule, and which TLS versions and suites older models accept today. Settle: *hardware*, the fingerprint and negotiated suite logged at every connect over a week, with reboots, on old and new models.
- **G5 Live WAV and FLAC** (C63). Unknown: whether each model plays WAV whose size fields hold their largest value, whether playback stops when the declared size runs out (after about 6 h 12 min at 48 000 Hz), and whether native FLAC with an unknown length plays and starts as fast. Settle: *hardware*, per model and format, one start and one run longer than 6 h 30 min.
- **G6 HTTP behavior** (C59, C60). Unknown: whether every model accepts a chunked body for each format, what request headers it sends (`Range`, `Icy-MetaData` and others), and whether any model insists on `206`. Settle: *hardware*, the stream server logs each model's request header names (up to 24, the rest counted) and its User-Agent, Range and Icy-MetaData values, each up to 96 characters, with the stream token never logged; a fake-receiver test cannot answer it.
- **G7 Latency and drift** (C74, C75, C77, C79). Unknown: the startup latency per model and format with this sender, how much it varies between starts, and how fast it drifts. This gap decides whether Cast can ever be more than a measured offset. Settle: *hardware*, the host plays a click train to a local speaker and the Cast device, one microphone records both; ten starts per format, then a 60-minute run with the offset logged every minute. The result also decides whether C79's restart may ever run automatically.
- **G8 What `currentTime` means for a live stream** (C73, C78). Unknown: whether it advances with what is heard, from what zero, and how often the device reports it unasked. Settle: *hardware*, during the G7 run, log `currentTime` next to the measured offset and the duration sent.
- **G9 Start behavior** (C48, C52). Unknown: whether `BUFFERED` instead of `LIVE`, or an explicit `PLAY` after `LOAD`, changes how much the receiver buffers before `PLAYING`. Settle: *hardware*, G7's start measurement repeated for each variant.
- **G10 Metadata updates** (C54). Unknown: a way to change title, artist or artwork of a playing live item on the Default Media Receiver without a reload. Settle: Google's media and queue documentation read for such a message, then *hardware*, the candidate tried during playback.
- **G11 Volume** (C69). Unknown: whether devices round levels to `stepInterval`, and how `level` maps to loudness. Settle: *hardware*, levels in small steps sent and the reported level logged; loudness measured at a few levels. The loudness half is parked: no behavior here depends on it, since the slider sends its value as is (C69), and a per-model loudness curve would only serve a new feature.
- **G12 Device heartbeat timeout** (C35). Unknown: how long a device waits for a silent sender before it closes the channel. Settle: *hardware*, the sender stops answering `PING` and logs when the device closes.
- **G13 Newer firmware** (C26, C47). Unknown: whether any current device needs `contentUrl` instead of `contentId`, or a sender id other than `sender-0` for app traffic. Settle: *hardware*, the session run against the newest devices at hand; a failure there is retried with `contentUrl` set and a random sender id.
- **G14 Device authentication** (C31). Unknown: whether any device or firmware refuses a sender that skips the device authentication step. No source reports one. Settle: watch for a `CLOSE` or `LAUNCH_ERROR` right after connect on any device, and record the model and firmware.

## 10. Test map

The sender's tests run against a fake receiver in the same process: a TLS server on an ephemeral port with a self-signed certificate that speaks the framing of section 3, answers on the connection, heartbeat, receiver and media namespaces as this document describes, and acts as the device for the HTTP fetch, with switches for each case below (slow or missing replies, error replies, `CLOSE`, an app taken over, a fetch that never comes, a slow reader). A switch makes it a group: it listens on a port other than 8009, answers on the multizone namespace and can fetch the stream from several local addresses. A fake multicast DNS responder serves the discovery cases. Names are suggestions; what matters is what each test checks. Gaps marked *hardware* in section 9 can't be settled in CI.

| Test (suggested name) | Clauses | Checks |
|---|---|---|
| scope_limits | C1, C2, C4 to C7, C9 | a second Cast target in one stream, a member of the playing group included, is refused with a reason; no message carries a host name, user name or hardware address |
| audio_handoff_realtime | C8 | the host's write call does not allocate or block, checked with an allocation counter and a stalled network thread |
| discovery_browse | C10, C11, C15 | PTR, SRV, TXT and address records resolve to a device with the announced address and port; subtype instances are ignored |
