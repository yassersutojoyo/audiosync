# Development

Notes for building AudioSync yourself and finding your way around the code. For how to send changes, see [`CONTRIBUTING.md`](../CONTRIBUTING.md); for cutting a release, [`RELEASE.md`](../RELEASE.md).

## Building

You need macOS 15 (Sequoia) or later, the Command Line Tools for Xcode 16 or later (`xcode-select --install`), which bring Swift 6 and the `python3` the build uses, and a Rust toolchain for the audio core in `core/`: install it with [rustup](https://rustup.rs).

The first build needs network access: it adds the two Apple targets to your Rust toolchain and fetches the crates.io index for the core's test-only dependencies. Later builds work offline.

```bash
git clone https://github.com/yassersutojoyo/audiosync
cd audiosync
./setup.sh
```

`setup.sh` checks for Swift and a Rust toolchain, then runs `build.sh`.

After that, `./build.sh` is all you need day to day. It builds the app, signs it, and installs it to `/Applications`, or `~/Applications` if `/Applications` isn't writable, after quitting the running AudioSync. AirPlay is part of the app binary (the Rust core carries the sender), so there's nothing else to bundle. `./build.sh --no-install` stops before the install: it leaves the signed app in `.build/app/AudioSync.app` and doesn't quit anything. CI builds it that way and checks the bundle with `Tests/check-app-bundle.sh`, which you can also point at an installed copy.

The app links the audio core, the Rust crate in `core/` (see `core/NOTES.md`). `build.sh` first runs `scripts/build_core.sh`, which builds it for Apple silicon and Intel (with rustup, it adds a missing target itself) and joins both into one static library, `core/target/universal-apple-darwin/release/libaudiosync_core.a`. That library exports only the functions in `core/include/audiosync_core.h`, so none of the Rust standard library's own symbols can stand in for the system's. Next to it, `licenses/rust/` gets the notices the app ships for the Rust code inside: the standard library's, and in `crates.txt` those of the crates compiled into the core (`scripts/core_notices.py`, run with `python3`). A plain `swift build`, a scratch build included, links that file: run the script first, or the link stops with "library 'audiosync_core' not found".

Everything is built with `MACOSX_DEPLOYMENT_TARGET=15.0`, the app's `LSMinimumSystemVersion`, so the app runs on macOS 15 and later, whatever macOS the release is built on; `Tests/check-app-bundle.sh` checks that the binary targets it.

A few environment variables change what the scripts do:

- `AUDIOSYNC_INSTALL_DIR`: install somewhere other than `/Applications`
- `AUDIOSYNC_ADHOC=1`: sign ad-hoc instead of with the local identity
- `CODESIGN_IDENTITY`: sign with a Developer ID, given by its full name (see `RELEASE.md`)
- `ENTITLEMENTS`: entitlements for the app signature (Developer ID builds default to `AudioSync.entitlements`)

### Signing

On the first build, `build.sh` runs `make-local-cert.sh`, which creates a self-signed "AudioSync Local Code Signing" identity in its own keychain (`~/Library/Keychains/audiosync-signing.keychain-db`), with no password prompt and no trust settings. Every build is signed with it, so macOS sees each rebuild as the same app and the System Audio Recording permission sticks.

With an ad-hoc signature the code hash changes on every build, and the permission quietly stops working: the toggle in System Settings stays on, but capture is silent. That's why `build.sh` signs ad-hoc only with `AUDIOSYNC_ADHOC=1`, or when there's no local identity and `make-local-cert.sh` can't create one, and says so loudly. If the local identity exists but can't sign, the build stops before it quits or replaces the installed app.

## Running and testing

```bash
open -a AudioSync
Tests/run-tests.sh               # shellcheck, text and source checks, logic tests and the core suite (the app's wrappers of the core), no audio hardware
Tests/run-tests.sh --hardware    # adds a silent engine test on every real output device
```

The tests are standalone Swift files in `Tests/`, no XCTest. Run the `--hardware` variant too when you touch the audio path. The script builds the Rust core (`scripts/build_core.sh`) first, since the logic and core suites link it. The logic suite, `Tests/logictest.swift`, checks the app's decisions, the local delay model among them, and builds `UIStrings` with them, which brings the capture and the engine's parts along. The core suite, `Tests/coretest.swift`, checks the app's wrappers of the core (the session's parts, a local output's delay reader driven the way the renderers drive it, the equalizer, the volume curve and gain stage). The core's own tests (`cd core && cargo test`) cover the DSP, the delay reader and the rules themselves. The soak rules suite, `Tests/soakrulestest.swift`, checks the soak harness's memory-growth rule (`Tests/soakrules.swift`, see `docs/BENCHMARKS.md`) on made-up footprint series: a run that warms up and then stays flat passes, a steady leak fails, and so does a leak after a spike in the warm-up. `--hardware` runs the engine test.

[EDGE_CASES.md](EDGE_CASES.md) lists what AudioSync does when devices, the source, sleep or the network change mid-session (EC1 to EC13), which checks cover each case, and the manual steps for the rest.

The test run starts with `scripts/shellcheck.sh`, which checks every script in `scripts/shellcheck-files.txt` and fails if shellcheck is missing. CI runs the same script with the same pinned shellcheck version (different versions flag different things), so install that version: `brew install shellcheck` gives it today, and `scripts/shellcheck.sh --install <dir>` downloads exactly the pinned release (then put `<dir>` on your `PATH`). A new shell script goes into that list, or the check fails.

Next comes `scripts/privacy_check.py`, which fails on home-directory paths from a Mac or a Windows PC, LAN hostnames, private IP addresses and internal plan IDs in tracked files (its docstring has the details and the allowed placeholders). It also has a forbidden-names guard: a few names must never appear in the repository, and they can't be listed in a public script, so `scripts/forbidden-names.txt` holds only a salt and a salted SHA-256 per name, and the script hashes every short run of words in file contents, paths and commit messages (`--commits A..B`) against it. A hit names the place, never the text. The plain list is a local, untracked file (`$AUDIOSYNC_FORBIDDEN_NAMES`, or `info/forbidden-names` in the git directory); `--hash-names` rebuilds the hash file from it, and `--verify-names`, which `run-tests.sh` runs, checks that the two still match and skips when there's no local list. CI runs the self-test, which proves the guard on made-up names, then the tree check and the check of the pushed commits' messages.

Then `scripts/text_check.py` fails on em dashes in the public docs, and three greps over `Sources/AudioSync` keep known traps out: a call inside a `DebugTrace.log(...)` message (it only runs with the debug log on), a plain `@State` (a macro the Command Line Tools can't expand, so `./build.sh` would fail there while CI passes), and logging, locks, dispatch, string building or allocation in the code the capture and microphone IOProcs run. `Tests/cargolookuptest.sh` checks how the scripts find `cargo` off the `PATH`.

`Tests/soak.sh` (an hour of silent playback, judged against a baseline) and `Tests/bench.sh` (writes that baseline) take long, so `run-tests.sh` only compiles their harness. [BENCHMARKS.md](BENCHMARKS.md) explains both.

For a debug log, quit AudioSync and start it from Terminal:

```bash
AUDIOSYNC_DEBUG=1 /Applications/AudioSync.app/Contents/MacOS/AudioSync
```

It writes to `/tmp/audiosync-debug.log`, which starts over at every launch and stops at 50 MB with a line that says so. Each line starts with the time in UTC, like the Windows log; the first one names the app and macOS versions and the Mac's local time.

Every local output that's switched on has its own macOS volume and mute read through Core Audio (`DeviceVolume.swift`), and followed with property listeners until it's switched off or unplugged. The log gets one line when an output is first read (`output <UID> device volume: 13%, not muted; volume settable on the main element, …`), one when what its row shows changes (`fine → low`), and one per click on the fix, with what was written, how each write went and what the device reports afterwards. The only write is that click; nothing else touches a device's own volume.

`AUDIOSYNC_BT_IO_FRAMES` is a diagnostic switch for one listening session, not a setting: set to a whole number from 256 to 4096, every Bluetooth output (Classic or LE) asks macOS for that IO buffer size, clamped to the device's range, before it starts; other outputs, and every output without the variable, stay exactly as they are. It tells whether a smaller or bigger buffer changes the chop you hear with two or more Bluetooth outputs at once. With the debug log on, each Bluetooth output that starts gets one `BT IO buffer:` line with the device, its transport, the request, the device's range, the size before and the size read back. Try one size at or below 1024 and 4096 in the same setup. For example: `AUDIOSYNC_BT_IO_FRAMES=1024 AUDIOSYNC_DEBUG=1 /Applications/AudioSync.app/Contents/MacOS/AudioSync`.

Each local output gets an `output at 1 minute:` line and an `output stopped (…):` line. After the frames rendered, the reader's counters and the late callbacks, they end with the observer's values (S229 in `docs/ENGINE_SPEC.md`). `least slack` is the closest the output came to running out of audio at the start of a callback, counted from half a second into playing (`n/a` before that); below 0, a callback found too little and the slow-down or a dry read covered it. `floor drop` is how much earlier the callbacks came than when the output last anchored. `shortage` counts the frames the slow-down made up, `IO overloads` the times macOS reported that the device's IO cycle missed its deadline, and `output-time steps` the jumps of more than 1 ms in the device's output times. `Bluetooth outputs` is how many Bluetooth outputs were playing. Counts and extremes run from the output's start, so whatever differs between the two lines happened after the first minute. Once per session a `network:` line gives the Wi-Fi band, channel and signal strength; what macOS keeps back without Location Services reads `n/a`, and the network's name is never logged.

The Windows app has the same switch. Exit it from the tray icon's menu, then start it from PowerShell in the folder that holds `audiosync.exe`:

```powershell
$env:AUDIOSYNC_DEBUG=1; .\audiosync.exe
```

The log lands in `%TEMP%\audiosync-debug.log` and starts over at every launch; it stops at 50 MB with a line that says so. Each line starts with the time in UTC; the first lines name the app and Windows versions and the PC's local time, so you can line the two clocks up. After that it lists the outputs and sources it found, what you switched, what the session rules decided, every output and capture that started or stopped and why, device changes and errors. For AirPlay it lists the receivers found, changed or gone and whether each can play, every speaker added or removed with its volume and delay, each session's state (connecting, playing, trying again) and errors, the latency each speaker reports, the sender's L, and when the local outputs start or stop waiting for the AirPlay speakers, with every output whose delay changed. While streaming, a status line every five seconds shows the frames captured and, for each output, its delay, volume, how often it ran dry or had to correct drift, the frames its slow-down made up (`shortage`) and its `least slack` as on the Mac, and for each AirPlay speaker its packets sent, late and resent. The variable stays set until you close that PowerShell window.

Both logs hold no passwords, PINs, keys, IP addresses or account names, but they do name your speakers and devices (a speaker's name often includes someone's name) and list each AirPlay receiver's ID, which is usually its network hardware address. Look through a log before you attach it to a public issue, and replace any name you'd rather not share.

The Windows app keeps the user's choices in `%LOCALAPPDATA%\AudioSync\settings.json`, next to the AirPlay pairings (`windows/src/settings.rs`): the source (whole system, an app by its executable's file name, or an input device), what happens when the source app quits, each output's switch, volume and delay by endpoint ID, each AirPlay speaker's by the ID it announces, the AirPlay delay adjustment (`airplay_adjustment_ms`, −2000 to +20 000 ms, added to the sender's latency), the master volume, auto-connect marks, the names given to speakers (`speaker_names`, by speaker key, left out while empty), groups, the equalizer, View > Show Virtual Devices, View > Appearance, the web remote's switch and port, the Cast speakers added by address, File > AirPlay 2 (Experimental) and the main window's frame. It's plain JSON with a `version` field, now 2: an output's `delay_ms` is its offset relative to the reference output (−2000 to +20 000 ms). Format 1 kept each output's own trim (0 to 20 000 ms) there; a format 1 file is migrated once, when the first output list is in: every other output's trim minus the reference's becomes its offset, the reference's trim becomes the AirPlay adjustment, and the file is saved as format 2 (nothing is saved before that). The debug log notes the migration (`settings: … output delay(s) migrated to offsets relative to …`). The file is read once at launch, before the first device listing, and written at most twice a second (at a poll, when something changed) and once more when the app exits, always through a temporary file that is flushed and renamed over it, so a crash leaves the old file or the new one. Without a file the defaults apply. A read that fails for any reason but a missing file is tried once more half a second later (an antivirus scan or a backup tool may hold the file for a moment). A file that still can't be read, isn't valid JSON or comes from a newer version is ignored and the defaults apply, but it's never saved over unseen: before the first save over it, it's copied next to it under a name of its own with the UTC time, `settings.ignored-2026-10-20T051230Z.json` (`settings.newer-….json` for a newer version's), written as a new file, so no later copy ever replaces an older one (a copy with the same contents is reused). While the file still can't be read, every save is refused and the "couldn't save your settings" notice shows; an unreadable or damaged file is kept aside right at launch when it can be read then, otherwise as soon as it can (tried every few seconds, and before the first save), and a notice then says the settings couldn't be read at launch, that AudioSync started with the defaults, and names the copy, whether or not anything is changed. Fields it doesn't know are skipped, missing ones take their defaults, and values out of range are clamped. A device that's gone keeps its entry, and the backend gets those settings at launch, so it plays with them when it comes back. The debug log says what happened (`settings: read (format version 2)`, `settings: no file yet …`, `settings: ignored: …`, `settings: the file ignored at launch was kept as …`, `settings: saved`). To start over, quit AudioSync and delete the file.

The double-audio notice only shows up while streaming. To look at its guide without playing anything, also set `$env:AUDIOSYNC_PREVIEW_GUIDE="app"` (one app captured) or `"system"` (the whole system) before starting it: with the debug log on, the guide opens at launch for a made-up notice.

To look at the code prompt of an Apple TV pairing without an Apple TV, set `$env:AUDIOSYNC_PREVIEW_PIN="code"` (the TV shows a code) or `"wrong"` (after a wrong code): with the debug log on, the dialog opens at launch for a made-up Apple TV, and nothing is paired.

To check the windows in the other appearance without changing the Windows setting, use View > Appearance, or set `$env:AUDIOSYNC_PREVIEW_THEME="light"` or `"dark"` as well: with the debug log on, every window uses that color scheme for this run, the tray flyout included, and nothing is saved. The tray icon itself keeps following the taskbar's light or dark mode. The log also says whether each window got its Windows 11 frame (Mica in the title bar, the flyout's rounded corners).

## Where things are

Everything lives in `Sources/AudioSync`. [`ENGINE_SPEC.md`](ENGINE_SPEC.md) describes the engine's behavior clause by clause, and [`EDGE_CASES.md`](EDGE_CASES.md) what happens when devices, sleep or the engine change under a session. [`WINDOWS_AUDIO_ROUTING.md`](WINDOWS_AUDIO_ROUTING.md) weighs how the Windows version could avoid double audio when capturing an app, and how it detects it now. The audio path, roughly in order:

- `AudioSource.swift`, `ProcessTapCapture.swift`, `CaptureSupport.swift`: what to capture (system, one app, an input device) and the capture itself
- `Equalizer.swift`: the 10-band EQ's settings and presets (`EqualizerWindow.swift` is its window; the core runs the filters)
- `CoreEngine.swift`: the Rust core's engine parts: the shared delay buffer with one independent reader per speaker, the equalizer and the output gain
- `EngineParts.swift`: one session's set of those parts, and what the capture hands each captured block to
- `OutputRenderer.swift`: one Core Audio output per local speaker
- `SyncEngine.swift`: `StreamEngine`, which ties capture, local outputs and AudioSync's AirPlay sender together
- `LocalDelay.swift`: the local delay model: the reference, the hold-backs each local speaker plays at, the AirPlay delay and the one-time migration of older delays
- `CalibrationFlow.swift`, `CalibrationTap.swift`, `CalibrationMicrophone.swift`, `AppDelegate+Calibration.swift`, `CalibrationViews.swift`: measuring a local speaker's offset with the microphone: the decisions, the test signal's way into the delay buffer, the recording kept in memory only, the run itself and its control under the speaker's delay
- `CalibrateAllFlow.swift`, `AppDelegate+CalibrateAll.swift`, `CalibrateAllViews.swift`: Calibrate All Speakers: the decisions around the core's run and sheet, the run itself, and the left column's row with the results sheet
- `WebRemote.swift`, `WebRemoteModel.swift`: the web remote through the core, and what it publishes and applies
- `NativeAirPlay.swift`, `NativeAirPlayTap.swift`: AudioSync's own AirPlay sender through the core's C interface, and the capture's way into it
- `NativeAirPlayModel.swift`, `NativeReceiver.swift`: what the sender lists and plays, and the decisions the app makes from it, PIN and password pairing among them (`AirPlayPairing.swift` holds the access kinds and turn-off reasons)
- `TrackMetadata.swift`: the track's title, artist and album, and its artwork scaled to a small JPEG, for AirPlay speakers with a screen (`ReceiverInfo.swift` decides what they show)

The app side: `AppDelegate.swift` holds app state, launch and quit (with its decisions in `AppLifecycle.swift` and the saved settings in `AppSettings.swift`), and its extensions split out windows (`+Windows`), groups and auto-connect (`+Groups`), local outputs (`+Outputs`), AirPlay speakers (`+AirPlay`, `+NativeAirPlay`) and streaming and notices (`+Engine`). The UI is SwiftUI in `MainWindow.swift` and `MenuBar.swift`, with the app menus in `MainMenu.swift`. Smaller pieces: `AudioDevices.swift` (Core Audio device helpers), `Volume.swift` (the loudness curve), `SpeakerGroups.swift`, `NowPlaying.swift` (Spotify and Music), `Diagnostics.swift` (the debug log) and `main.swift` (keeps one copy running, and quits cleanly on Ctrl-C or SIGTERM).

The app's side of the Rust core (`core/`, imported through the `CAudioSyncCore` module in `Sources/CAudioSyncCore`): `CoreEngine.swift` wraps the core's engine parts, `EngineParts.swift` makes one set of them for each session, and `AudioSyncCore.swift` logs the core's version at launch.

All user-facing text goes through `UIStrings` in `Localization.swift`. `Brand.swift` turns the design tokens into SwiftUI colors, the typeface and the wordmark; the values themselves live in `brand/tokens.json` and reach the app through the generated `BrandTokens.swift`. `BrandMark.swift` and `BrandTokens.swift` are generated, so don't edit them.

Outside the app: `setup.sh` checks the tools and runs `build.sh`, which builds, signs and installs the app, `scripts/build_core.sh` builds the Rust core, and `make-dmg.sh` packages a release (see `RELEASE.md`).

## The Rust core and the Windows app

Two Rust folders sit next to the Swift package.

`core/` is `audiosync-core`, the platform-independent audio core: the delay ring buffer, drift correction, resampling, the equalizer, volume, the output stage's sample conversion and the sync policies. It's written from [`ENGINE_SPEC.md`](ENGINE_SPEC.md), and [`core/NOTES.md`](../core/NOTES.md) records how it reads the spec where there was room to choose. The macOS app links it as described under Building. Its tests need only a Rust toolchain, no audio hardware:

```bash
cd core && cargo test
```

`windows/` is a Windows 11 version of AudioSync in development, written in Rust with a [Slint](https://slint.dev) interface. It gets its audio work from the same core: the ring, the delay readers, the renderer with its 20 ms fades, the resampler, the volume curve, the equalizer and the session rules. Every output fades in on its first audio and out before it stops, and a delay change fades out and back in, so starts, stops and source changes don't click. A stop or a source change doesn't hold up the window while the outputs fade: each output's thread keeps its stream running until the device has played the fade (at most 500 ms), the backend's next poll stops what has faded, the old capture last, and a new source's capture starts at the poll after the old one's outputs have faded. Its screens (the main window, the equalizer, a tray icon with a flyout, the Guide, the web remote's window and the About dialog) drive a WASAPI backend on Windows that captures one app or the whole system through process loopback, or an input device, and plays it on the outputs you turn on; on any other host the window shows example speakers from a mock backend instead. [`windows/README.md`](../windows/README.md) says what has been tried on a real PC so far. CI checks the formatting, runs clippy and the tests, and builds it for x64 and ARM64, each build with the license notices `scripts/windows_notices.py` writes for it. On Windows you need rustup with the stable MSVC toolchain and the Visual Studio Build Tools ("Desktop development with C++"), then `cargo test` and `cargo build --release` in `windows/`. On a Mac, `cargo test` runs its logic tests and `cargo check --target x86_64-pc-windows-msvc` checks the Windows code, but can't link it. [`windows/README.md`](../windows/README.md) has the details, and [`WINDOWS_AUDIO_ROUTING.md`](WINDOWS_AUDIO_ROUTING.md) weighs how it could capture one app without playing it twice.

`airplay/` is `audiosync-airplay`, AudioSync's own AirPlay sender, which both apps use for AirPlay speakers (the Mac app through the core, see below). It's written from [`AIRPLAY_SPEC.md`](AIRPLAY_SPEC.md), and [`airplay/NOTES.md`](../airplay/NOTES.md) records its readings of the spec. It covers discovery, the AirPlay 1 session and one stream to many speakers, plus Apple TV PIN pairing. The Windows app asks for the code when you switch such an Apple TV on, and keeps the credentials per speaker in `%LOCALAPPDATA%\AudioSync\airplay-pairings.dat`, encrypted with DPAPI for the current Windows user (`windows/src/audio/pairings.rs`); a file it can't read (even at a second try, a moment later) or decrypt is ignored, and those speakers pair again; the ignored file is kept as `airplay-pairings.ignored-<UTC time>.dat`, a new copy no later one replaces, right at launch when it can be read then (otherwise as soon as it can: tried every few seconds and before the next pairing writes a new file), a notice then names that copy, and nothing is written over a file that still can't be read. Its CI checks the formatting, runs clippy and `cargo test` (including a check that the tests cover the spec), and lets in only permissive licenses (`cargo deny check licenses` with `airplay/deny.toml`).

The AirPlay 2 path is off by default until it passes a check on a real receiver. On the Mac, 'AirPlay 2 (Experimental)' in the gear menu or the AudioSync menu turns it on from the next launch (`airPlay2Enabled` in UserDefaults, passed to `asc_airplay_create_with_airplay2`); on Windows it's File > AirPlay 2 (Experimental), also from the next launch. Both apps also read `AUDIOSYNC_AIRPLAY2` when they start the sender (`AppSettings.airPlay2On` on the Mac, `windows/src/audio/airplay.rs` on Windows), and the value `1` turns it on without the switch, for CI and debug runs. While it's off, nothing of the AirPlay 2 path runs. With it on, the sender can reach a receiver over AirPlay 2, with PIN pairing and PTP timing, and plays one AirPlay 2 speaker at a time: a second one waits for the slot, with a note under its name, and starts when the first stops. Rows reached over AirPlay 2 carry an AirPlay 2 label.

With the switch on, discovery also reports stereo pairs and home theater groups (an Apple TV with the HomePods it plays through) as targets (`AIRPLAY_SPEC.md` P171 to P181, in `airplay/src/targets.rs`). A target's ID is `pair:<tsid>` for a pair and `theater:<group key>` for a home theater group, lowercased, and it stays the same while the members' `gid` changes form, so a target's switch, volume and delay are stored under that ID. Playing a target opens one session per member, all on one path, each with the same stereo mix, one delay and one volume; under PTP the members share one PTP service. For the one-at-a-time rule a target counts as one AirPlay 2 speaker. A member that's missing or lost marks the target incomplete, and the others keep playing. The core lists a target like a speaker with `ASC_AIRPLAY_FLAG_TARGET`, plus `ASC_AIRPLAY_FLAG_INCOMPLETE` while a member is out (`core/include/audiosync_core.h`). Both apps show a target as one row that names its members, or the one that's missing; its members show as rows only while they're on by themselves, and are switched off when the target takes over.

For debug runs, `AUDIOSYNC_AIRPLAY_PCM=<id>[,<id>…]` lets the listed speakers use uncompressed PCM instead of ALAC where they offer it (`AIRPLAY_SPEC.md` P74), read by `core/src/ffi/airplay.rs` on the Mac and `windows/src/audio/airplay.rs` on Windows. IDs are the ones the debug log shows; a device ID may be written with colons or in lowercase (`aa:bb:cc:dd:ee:ff`). A stereo pair or home theater group takes PCM only through its target ID (`pair:…`, `theater:…`), for all its members. Each app logs a line when a listed speaker joins, and a receiver that refuses PCM gets ALAC.

`cast/` is `audiosync-cast`, AudioSync's own Google Cast sender, which both apps use: the Windows app through `windows/src/audio/cast.rs`, the Mac app through the core's `asc_cast_*` C interface (`core/src/ffi/cast.rs`, wrapped by `CastSender.swift`, with `CastTap.swift` as the capture's way in and `CastModel.swift` for the decisions). It's written from [`CAST_SPEC.md`](CAST_SPEC.md). It finds devices over `_googlecast._tcp`, opens the Cast channel over TLS with the platform's own TLS stack, launches the Default Media Receiver and has it fetch a live WAV stream from a small HTTP server in the app, with FLAC as the fallback for devices that need it, plus device volume, mute, recovery and Resync. One worker thread (`CastHost` in `cast/src/host.rs`) makes every network call; the apps send commands and poll events, so their UI thread never waits on the network. One Cast device plays at a time. A Cast group (a speaker group made in the Google Home app) plays as one target over one channel to the group's own port, with one volume and one offset, and its members are read from the group's multizone status (`CAST_SPEC.md` C89 to C103). Both apps show a group as one row that names its members once the session reports them, and keep its offset under the group's own ID; a member stays a row of its own. Cast has no shared clock, so a device is kept in step only by an offset the user sets by ear; it's kept per device with the device's audio format, in `cast-devices.json` in AudioSync's Application Support folder on the Mac and `cast-speakers.json` in the app's data folder on Windows. Local outputs wait that offset for the device but never wait for it to start. Resync restarts the stream with a short gap and is only ever a user action. Its CI checks the formatting, runs clippy and the tests, and lets in only permissive licenses, development dependencies included (`cargo deny check licenses` with `cast/deny.toml`).

With AirPlay speakers and a Cast device on together, the side with the shorter latency waits for the other (`CAST_SPEC.md` C77 for the AirPlay side; the Cast feed waiting is AudioSync design). If the Cast offset is longer than the AirPlay latency, the AirPlay speakers wait the difference, up to the sender's 20 000 ms limit per speaker (`asc_airplay_set_hold_back` on the Mac, the hold-back added to every speaker's delay in `windows/src/audio/airplay.rs`); past that limit the AirPlay speakers play ahead of the Cast device, and a notice says by how much and suggests a lower offset. If the AirPlay latency is longer, the Cast feed goes through a delay line in front of its ring and waits the difference, up to 20 s (`asc_cast_set_hold_back` on the Mac, `CastSpeakers::set_hold_back` on Windows). `NetworkHoldBack` in `CastModel.swift` holds the Mac's arithmetic.

`remote/` is `audiosync-remote`, the web remote: a small hand-written HTTP/1.1 server (std sockets, no web framework) that serves one page from the binary plus a JSON API and a Server-Sent Events stream, so a paired phone on the home network can switch speakers, set their volume and delay, and set the master volume. It's off until the user turns it on, and listens on port 7655 by default, which is unassigned in the IANA port registry. The app publishes a full snapshot whenever something the page shows changes and gets each change back through one callback on a server thread, so the server never reads app state on its own. The connection is plain HTTP, so the server protects itself: only private, link-local and loopback peers, plus IPv6 peers in the machine's own /64 (a phone with a global address on the same network), get an answer, the `Host` header has to name the machine, every `POST` needs a matching `Origin` and a JSON body, and the API wants a device token that a single-use 6-digit pairing code buys. A code works for 10 minutes. 5 wrong codes a minute from one address, or 10 before the code is renewed, refuse only that address; 40 from all addresses together lock pairing for everyone until then. The token travels only in the `as_token` cookie (`HttpOnly`, `SameSite=Strict`, kept 400 days). Only the tokens' SHA-256 hashes are stored, for at most 8 devices, in `RemoteDevices.json` in AudioSync's Application Support folder on the Mac and `remote-devices.json` in the app's data folder on Windows. The server holds 32 connections, one address 8 of them; 8 of the 32 stay for requests carrying a paired device's token, so slow unpaired clients can't keep a paired phone out; when every slot is taken, the oldest connection still waiting unpaired in one of those 8 is closed to let a new one in, and the accept loop drains a refused connection for up to 1 s before closing it, so its 503 is not lost to a reset. One device holds 2 event streams; a third ends the oldest, which gets a last `replaced` event, so that page waits for its Retry button instead of reconnecting and ending the next one. The page's Content-Security-Policy allows its one inline script and style by hash, computed at startup. The Mac app reaches it through the core's `asc_remote_*` C interface (`core/src/ffi/remote.rs`, wrapped by `WebRemote.swift`), from 'Web Remote…' in the gear menu or the Window menu. The Windows app uses the crate directly, from File > Web Remote… (`windows/src/remote.rs` for the setting, the snapshot and the commands, `windows/src/view/remote_window.rs` for the window and the server); its port setting takes 1024 and up. Both apps turn a command from the page into what the window's own control would do. `remote/page/index.html` is the whole page, with one inline style and one inline script so the CSP can name both by hash; it borrows the site's icons until it has its own. Its CI (`.github/workflows/remote.yml`) checks the formatting, runs clippy and the tests over real sockets on 127.0.0.1, and lets in only permissive licenses (`remote/deny.toml`).

Microphone calibration lives in the core, so both apps measure the same way. `core/src/calibrate.rs` makes the test sweep and finds where it arrives in a recording (`ENGINE_SPEC.md` S232 to S234); the apps play it and record the default input device, the Mac through `CalibrationMicrophone.swift`, Windows through `windows/src/audio/wasapi/microphone.rs` (shared mode, float, mixed to mono, stamped with the core's clock). On Windows, 'Calibrate with Microphone' on a local speaker's row runs `windows/src/audio/calibration.rs`: the music fades out, the sweep plays on the reference alone and then on the chosen output alone, and the estimate becomes that output's new offset. A cancel or any change during the runs leaves the offset as it was.

Calibrate All Speakers (S235 to S240) measures the reference and then every speaker that is on, local, AirPlay and Cast alike, one at a time and twice each, while the others stay silent. `core/src/calibrate_all.rs` (`asc_calibration_run_*` in `core/src/ffi/calibrate_all.rs`) says what to play next and how long to record, and turns the recordings into a results sheet; it never changes a delay itself. A local row moves that output's offset, a Cast row the Cast speaker's offset (0 to 20 000 ms on the sheet), and the AirPlay rows share the one AirPlay delay, set to the median of the certain rows. A row more than 10 ms uncertain keeps its delay, and AirPlay rows more than 10 ms apart get a note, since one delay can't cover them. The user applies the sheet, undoes it in one step, or measures a row again. The Mac runs it from `AppDelegate+CalibrateAll.swift` with the sheet in `CalibrateAllViews.swift`; Windows from `windows/src/audio/calibrate_all.rs`, shown in the main window's Calibrate All Speakers card. A change to what the run depends on stops it.

### Running the engine on the Rust core

The app's audio engine runs on the core. Capture (the process tap or input device) and the Core Audio output units stay in Swift, while the delay ring, the per-speaker delay readers with their drift correction, the equalizer, the volume curve and output gain come from `core/`, and the AirPlay audio goes to the sender in `airplay/`. Each session gets its own set of the core's parts when streaming starts; should the core fail to make them, streaming doesn't start and the debug log says why. Builds before 2026-10-19 also had the Swift engine the core replaced, chosen by the `engineImpl` setting or `AUDIOSYNC_ENGINE`; both are ignored now: a launch that finds either one notes it in the debug log, and removes the setting, so only a variable still set is noted again. Each local output renders through the core's renderer with its 20 ms fades (the spec's S182 to S191, `AscRenderer`): the output unit takes the device's own rate and channels, a new renderer is made at each start, each callback keeps the output's delay reader at least a lead ahead (one device callback, plus the capture's block for an output that converts rates, such as a 44.1 kHz device under 48 kHz capture, S206) so it doesn't run dry, and every output fades in on its first audio and fades out and back in around a delay change, the local delay model's re-timings included. A stop asks every output and the native AirPlay input to fade out at once and keeps capturing until the outputs' devices have played their fades (the fade's last output time, from the render callback's time stamp, plus the device's and stream's latency) and the native input has had its fade's 20 ms of audio, also with only AirPlay speakers on, at most 500 ms; then capture and the outputs stop. Switching speakers off fades them the same way. Neither holds up the main thread: a short timer finishes them. Only a start right after a stop (a source change) and quitting wait for the fades, at most 500 ms. The native AirPlay input fades in after each rate set, that is at each capture build.

Local delays follow the local delay model (`ENGINE_SPEC.md` S172 to S181, `LocalDelay.swift`, through the core's `asc_local_*` calls). The reference is the first built-in output whose first output stream reports the speaker terminal type, else the first built-in output, chosen afresh from every device list (`AudioDevices.Device.outputTerminal` is read for built-in outputs only). Every other local speaker has an offset from −2000 to +20 000 ms, stored by device UID under `localOffsetMsByUID`; the core turns the offsets of the speakers that are on and listed into hold-backs, and `retimeLocalOutputs()` in `AppDelegate+Outputs.swift` hands a running renderer a new hold-back only when its own changed. The AirPlay delay is `nativeAirPlayAdjustmentMs`, added to the latency AudioSync's AirPlay sender reports (0 by default); `airPlayDelayMs`, L itself from the builds that bundled an AirPlay engine, is still kept but no longer applies. Builds before the model stored absolute delays under `localDelayMsByUID` (and an older single one under `delayMs`); the first launch with a device list migrates them once, before auto-connect, sets `localDelayModelMigrated` last, and leaves the old keys alone for older builds. The debug log notes the migration (`delays migrated to offsets relative to …`) and every re-timing (`local delays re-timed: …`).

AudioSync's own AirPlay sender (`airplay/`, the one the Windows app uses) is the Mac app's AirPlay sender, through the core's C interface (`asc_airplay_*`, wrapped by `NativeAirPlay.swift`). Builds that also bundled an AirPlay engine chose between the two with the `airplayImpl` setting or `AUDIOSYNC_AIRPLAY`; both are ignored now: a launch that finds either one notes it in the debug log, and removes the setting, so only a variable still set is noted again. The AirPlay rows are the receivers the sender's discovery finds (without this Mac's own AirPlay Receiver), switching one on adds it to the sender while streaming, its volume and the master go to it, the track and artwork from Now Playing go to the receivers that show them (`asc_airplay_set_now_playing`, the artwork as a JPEG of at most 600 px a side and 6060 bytes), with the track's position and length from Spotify or Music for receivers that show progress (`asc_airplay_set_progress`, sent with a new track, a seek or a pause and dropped by the next track), and its errors show as notices. An Apple TV that asks for a PIN pairs once, when you switch it on, and its credentials are kept in the pairing store (`airplay-pairings.dat` in `Pairings` inside AudioSync's Application Support folder). `NativeAirPlayPairings` marks that folder as excluded from backups before the store opens, since the file is plaintext: the folder rather than the file, because every write renames a new file over the old one, and only that folder, because AudioSync's own folder also holds `signing-keychain.pass` on a Mac that signs builds (`make-local-cert.sh`) and must stay in backups along with its keychain. A file that earlier builds kept directly in AudioSync's folder moves into `Pairings` once, unless `Pairings` already has one. A speaker with a password asks for it once per launch, and the password (like a PIN on its way to the sender) is held inside the sender as a `Secret` (`airplay/src/secret.rs`), wiped from memory when dropped, never printed and compared in constant time; the host's text field and the strings that hand it over aren't wiped. The capture feeds the sender through `NativeAirPlayTap` (from `EngineParts`), which resamples to 44.1 kHz without allocating. While a native speaker is chosen, local speakers wait the sender's latency plus the AirPlay delay adjustment, on top of their offsets (S178); the window's AirPlay delay field shows that sum, and editing it stores the difference to the latency of that moment. Native rows use their own IDs (`native:` and the receiver ID). Speakers saved under the bundled engine's IDs (switched on, volumes, groups, auto-connect) move to those the first time discovery finds their receiver, matched by device ID (`SpeakerIDMigration`, S204); the debug log has a line for each (`settings saved under the bundled engine's ID …`). The debug log lists every receiver found, every speaker added or removed and every state, error and latency (`native AirPlay: …`). If the sender can't start (or can't browse the network), a notice says so and the app tries again every 10 s or so. A bug in the sender doesn't take the app down: the core's release build unwinds, every `asc_airplay_*` call catches a panic (as does the sender's driver thread, through `Sender::is_running`), and a dead sender reports `ASC_AIRPLAY_EVENT_FAILED` once; the AirPlay section then shows it as stopped, with a notice and a Retry button that starts a new one. The debug log's line for that failure says where the panic happened, as a source file and line (`… after an internal error (panic at airplay/src/sender/driver.rs:123)`), never what the panic said (S205). CI proves the catching in the library the app links: `AUDIOSYNC_CORE_PROBE=1 scripts/build_core.sh` builds it, prelinked the same way, with one extra entry that panics inside a sender call's guard (the core's `ffi-panic-probe` feature, never in the app's library), and `Tests/panic-probe.c` calls it and expects the failure, then a normal exit. A panic anywhere else in the core still ends the app, since unwinding out of any other `extern "C"` function aborts.

## Logo, icons and screenshots

The logo, app icon and wordmark are generated from the sources in `brand/` by `scripts/brand/build-brand.sh`; [`brand/README.md`](../brand/README.md) explains how. Don't edit `AppIcon.icns`, `icon-source.png`, the `site/` icons, `site/wordmark.svg`, `BrandMark.swift` or the Windows icons in `windows/res/` (from `scripts/brand/windows-icons.sh`) by hand.

The design tokens (colors for light and dark, the typeface, spacing, corner radii and opacities) live in `brand/tokens.json`. `python3 -I scripts/brand/tokens.py` writes them into `Sources/AudioSync/BrandTokens.swift` for the Mac app, `windows/ui/tokens.slint` and `windows/src/tokens.rs` for the Windows app and its contrast test, and the CSS variables between the `tokens:begin` and `tokens:end` comments in `site/index.html`; `--check` only reports what's out of date. Change a token in the JSON and rerun the script, never the outputs.

The Guide's three illustrations (the signal path, what a delay does, and the two kinds of output timing) are drawn in code by `python3 -I scripts/brand/guide_art.py`, in five colors taken or mixed from the tokens. The script checks that those colors keep shapes at 4.5:1 or more against both Guides' pages and the panels in both appearances, writes the light and dark SVGs to `brand/guide/`, and embeds both in `Sources/AudioSync/GuideArtwork.swift`; where each one sits in the Mac Guide's text is `guideArtAnchor` in `Localization.swift`. The Windows Guide (`windows/ui/help.slint`) loads the same SVGs, light or dark with the theme. With `--check` the script writes nothing and fails when any of those files is out of date, which is how CI runs it. Every image's origin is recorded in [`ASSETS.md`](ASSETS.md).

CI regenerates the brand SVGs, `BrandMark.swift`, `GuideArtwork.swift` and every token output and fails on any difference, but it doesn't check the PNG, ICNS and ICO files (including `windows/res/`), so regenerate those yourself.

The screenshots in `docs/images` come from `scripts/screenshots/render.sh`. It draws the app's own SwiftUI views offscreen from mock data, in light and dark, so it needs no installed app, engine, permissions or audio devices. Control styling follows the macOS you run it on, so re-render after a UI change.

## Uninstalling

If this is the Mac that builds releases, stop first: removing `~/Library/Application Support/AudioSync` also deletes `signing-keychain.pass`, the password of the release signing keychain. Back up both (see `RELEASE.md`).

Otherwise, turn off Launch at Login in the gear menu, quit AudioSync, and run:

```bash
rm -rf /Applications/AudioSync.app ~/Applications/AudioSync.app \
  ~/Library/Application\ Support/AudioSync \
  ~/Library/Caches/io.github.yassersutojoyo.audiosync \
  ~/Library/HTTPStorages/io.github.yassersutojoyo.audiosync
defaults delete io.github.yassersutojoyo.audiosync
tccutil reset All io.github.yassersutojoyo.audiosync
security delete-keychain ~/Library/Keychains/audiosync-signing.keychain-db   # if you built it yourself
rm -rf ~/.audiosync-build   # older builds built their AirPlay engine here
```

Older builds that bundled an AirPlay engine also installed the Homebrew build tools `pkg-config` and `cmake` (plus `nasm` on Intel Macs); `brew uninstall` them if nothing else needs them.
