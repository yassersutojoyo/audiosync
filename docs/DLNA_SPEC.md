# AudioSync DLNA / UPnP AV sender specification

A behavioral specification for a UPnP AV sender in AudioSync: a component that finds UPnP media renderers (the devices DLNA calls Digital Media Renderers) on the local network, has one of them fetch the host's live audio over HTTP from the host, and controls its transport and volume. It is written so the sender can be built by someone who reads only this document, the UPnP Forum documents and RFCs it cites, and the documentation of the crates they choose.

UPnP AV is a third network output class next to AirPlay and Google Cast, and it is a measured-offset output like Cast (`docs/CAST_SPEC.md` C77): nothing in the protocol a sender can rely on ties a sample to a time, so the host keeps other outputs in step with a renderer only through that renderer's measured latency and the user's per-speaker delay. Section 7 says what the sender can and cannot control.

Provenance. Written on 2026-10-30 from public sources: the UPnP Forum's Device Architecture and AV specifications, the public previews and tables of contents of the DLNA guidelines as published by the IEC, press coverage of the DLNA guidelines, a public user report, the RFCs, and a read-only black-box look at the local network (section 11). Facts are restated in our own words. No code, and no paraphrase of code, from any implementation is in this document. Every URL in the Sources list was fetched on 2026-10-30.

## Conventions

- MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are normative, in the sense of RFC 2119.
- Each clause states one behavior of the sender. It ends with *Source:* (the kind of source the fact comes from; "derived" means reasoned from facts in the cited sources rather than stated there) and, where AudioSync needs something the sources don't settle, *Required:* (the choice the sender MUST implement). "*Source:* AudioSync design" marks a clause that is a requirement only.
- A *Source:* of "public user report" quotes what one user posted about one device. It is one observation, not a rule.
- Terms: *sender* is the component this document specifies; *renderer* is a UPnP device of type MediaRenderer; *control point* is the UPnP role the sender plays; *description* is the renderer's device description document, *SCPD* a service's description document; *action* is one SOAP request and its response; *session* is the time from the sender's `SetAVTransportURI` to its `Stop` or the end of the renderer's fetch; *stream server* is the host's HTTP server that the renderer fetches the audio from.
- Action, argument and state variable names are written as they appear on the wire, such as `SetAVTransportURI` and `CurrentURIMetaData`; they are case-sensitive.
- Example addresses use 192.0.2.0/24 (RFC 5737).
- Clause IDs run from U1 without gaps in this version. A clause added later takes the next free number and sits in the section it belongs to; a dropped clause keeps its number, marked withdrawn. Gaps are numbered UG1 onward.

## 1. Scope and role

- **U1** The sender handles audio only. It never sends video, images or text tracks to a renderer. *Source:* AudioSync design.
- **U2** The sender plays the UPnP AV role the architecture calls a control point with content: it serves the content itself and drives only the renderer's services, with no MediaServer and no ContentDirectory service in between. *Source:* UPnP AV Architecture:1 §3.3.2 [av-arch] (control point with content, which "only interacts with the MediaRenderer services").
- **U3** The transfer is HTTP GET pulled by the renderer (`http-get` in ConnectionManager terms). RTSP/RTP, IEEE 1394 and the renderer-side push models are not used. *Source:* ConnectionManager:1 §2.5.2 and §5.1.1 [cm1]; UPnP AV Architecture:1 §4.2 [av-arch].
- **U4** A stream drives at most one renderer in this version. Starting a stream on a second renderer while one plays is refused with a clear reason. UPnP AV has no group concept a sender could address as one target. *Source:* AudioSync design; UG6 tracks lifting the limit.
- **U5** Out of scope: DRM and DTCP-IP link protection (protected content is never sent and a renderer that accepts only protected content is unsupported); video and images; serving or browsing a ContentDirectory; recording (`Record`); playlists and gapless next items (`SetNextAVTransportURI`); `Seek`, `Pause`, `Next`, `Previous`; `PrepareForConnection` and `ConnectionComplete`; the CLOCKSYNC synchronized playback feature of AVTransport:3 (UG5); UPnP device security; renderers reached only across a router. *Source:* AudioSync design; Wikipedia, Digital Living Network Alliance [wiki-dlna] (DTCP-IP as link protection for copyright-protected content).

## 2. Discovery

- **U6** The sender finds renderers with SSDP: a multicast `M-SEARCH * HTTP/1.1` to 239.255.255.250:1900 with `HOST: 239.255.255.250:1900`, `MAN: "ssdp:discover"`, `MX: 2` and `ST: urn:schemas-upnp-org:device:MediaRenderer:1`, and no body. The datagram's TTL is 2. *Source:* UPnP Device Architecture 1.1 §1.3.2 [uda11] (required header fields; MX at least 1 and at most 5; default TTL 2).
- **U7** It searches for version 1 on purpose. A device that implements a later version of a type MUST answer a search for an earlier version, and its response carries the version that was searched for; the versions a renderer really implements are read from its description (U11). *Source:* UPnP Device Architecture 1.1 §1.3.2 [uda11].
- **U8** Each search is sent twice, 500 ms apart, since UDP may lose it, and the sender listens for answers for at least MX plus 1 s after the second send. Responses are unicast to the source address and port of the search, so the socket that sends the search receives them; it is bound to the address of one local interface with an ephemeral port, one socket per interface, never to a wildcard address. *Source:* UPnP Device Architecture 1.1 §1.3.2 (send more than once; wait at least MX) and §1.3.3 (unicast response to the source address and port) [uda11]; AudioSync design (interface binding, so no listener on a wildcard address is opened).
- **U9** While renderer discovery is on, the sender searches when it starts, every 60 s after that, and when the host's network interfaces change. It does not join the SSDP multicast group to hear `NOTIFY` announcements in this version. A renderer that answered no search for longer than the `max-age` of its last `CACHE-CONTROL`, or whose description fetch fails twice in a row, is dropped from the list. *Source:* UPnP Device Architecture 1.1 §1.3.3 (`CACHE-CONTROL: max-age`, after which the device is assumed gone) [uda11]; AudioSync design.
- **U10** From a search response the sender reads `LOCATION` (the absolute URL of the root device's description), `ST`, `USN` and `CACHE-CONTROL`. A response whose `LOCATION` is not an `http` URL, or whose host is not the literal IP address the response came from, is ignored. *Source:* UPnP Device Architecture 1.1 §1.3.3 [uda11] (`LOCATION` is an absolute URL, normally with a literal IP address, reachable on the interface the search came in on); AudioSync design (the address check keeps a response from pointing the sender at a third host).
- **U11** The sender fetches the description with HTTP GET and reads, for the device whose `deviceType` starts with `urn:schemas-upnp-org:device:MediaRenderer:` (the root device or a device in its `deviceList`): `UDN`, `friendlyName`, `manufacturer`, `modelName`, and from its `serviceList` each `service`'s `serviceType`, `serviceId`, `SCPDURL`, `controlURL` and `eventSubURL`. *Source:* UPnP Device Architecture 1.1 §2.3 [uda11]; MediaRenderer:1 §2.2 and its sample description [mr1].
- **U12** Relative URLs in a description are resolved against `URLBase` when the description has one (a UPnP 1.0 device), otherwise against the URL the description was fetched from, by the rules of RFC 3986 §5. *Source:* UPnP Device Architecture 1.1 §2.3 [uda11] (UPnP 1.1 devices must not send `URLBase`; control points must still honor it).
- **U13** A renderer is usable only if its device lists RenderingControl, ConnectionManager and AVTransport services (any version). RenderingControl and ConnectionManager are required of every MediaRenderer; AVTransport is present when the renderer supports a transfer protocol that needs it, as HTTP GET does. A renderer without AVTransport is listed as unsupported, with that reason. *Source:* MediaRenderer:1 §2.2.1 [mr1].
- **U14** The `UDN` is the renderer's identity: the stored offset (U38), the remembered format (U24) and the selection are kept under it. `friendlyName` is the name shown in the host. When a later search shows the same `UDN` at another `LOCATION`, the entry moves to the new address. *Source:* UPnP Device Architecture 1.1 §1.1.4 and §2.3 [uda11] (UDN as the device's unique identifier); AudioSync design.
- **U15** A renderer whose description address is one of the host's own addresses is not offered: playing the host's captured audio on a renderer in the same computer feeds that audio back into the capture. *Source:* AudioSync design; section 11 (the one search made for this document found two renderers that Windows itself provides).
- **U16** For the AVTransport and RenderingControl services the sender fetches the SCPD once per discovered renderer and reads its `actionList` and the `allowedValueRange` of the `Volume` state variable. An action the SCPD does not list is treated as absent. *Source:* UPnP Device Architecture 1.1 §2.5 [uda11]; RenderingControl:1 Table 2-13 [rc1] (`Volume` minimum 0, maximum vendor defined, step 1).

## 3. Control

- **U17** Every action is an HTTP POST to the service's `controlURL` with `CONTENT-TYPE: text/xml; charset="utf-8"`, `SOAPACTION: "<serviceType>#<actionName>"` (the quotes are part of the value; `<serviceType>` is the full type URN as the description lists it, version included), a `CONTENT-LENGTH` (never a chunked request body), and a SOAP 1.1 envelope with `encodingStyle` `http://schemas.xmlsoap.org/soap/encoding/` whose body holds one element named after the action in the service type's namespace, with the in arguments as child elements in the order the SCPD lists them. The sender never uses `M-POST`. *Source:* UPnP Device Architecture 1.1 §3.2.1 [uda11].
- **U18** Argument values are XML-escaped text. An argument whose value is itself an XML document (`CurrentURIMetaData`, U27) is escaped as text once, like any other string. *Source:* UPnP Device Architecture 1.1 §3.2.1 [uda11] (arguments are strings in the body of the SOAP message); derived.
- **U19** Every AVTransport and RenderingControl action uses `InstanceID` 0. Without `PrepareForConnection` a control point falls back to instance 0, and the sender never calls `PrepareForConnection`. *Source:* UPnP AV Architecture:1 §4.7 and §3.2.1 [av-arch].
- **U20** A device must answer an action within 30 s. The sender waits at most 10 s, then treats the action as failed with a timeout. *Source:* UPnP Device Architecture 1.1 §3.2.2 and §3.2.5 [uda11] (response within 30 s); AudioSync design (10 s keeps the host responsive; a reply that takes longer is a failure the user sees).
- **U21** An action error arrives as HTTP 500 with a SOAP fault whose `detail` holds a `UPnPError` with `errorCode` and `errorDescription`. The sender logs both and handles the codes of section 8; codes 401 (invalid action), 402 (invalid args) and 600 to 699 are faults the host reports with their description. *Source:* UPnP Device Architecture 1.1 §3.2.5 and Table 3-3 [uda11]; AVTransport:1 §2.4.18 [avt1].

## 4. Starting a session

- **U22** The sender calls ConnectionManager `GetProtocolInfo` and reads the `Sink` output: a comma-separated list of protocolInfo strings, each `<protocol>:<network>:<contentFormat>:<additionalInfo>`. For HTTP GET the protocol is `http-get`, the network is `*` and the content format is a MIME type. `*` in any of the first three fields matches anything; the fourth field need not match between source and sink. *Source:* ConnectionManager:1 §2.2.2, §2.4.1, §2.5.2 and §5.1.1 [cm1].
- **U23** The sender picks the format by the sink list (formats in section 6): `audio/L16` at the stream's rate with `channels=2` first, then `audio/wav`, then `audio/x-wav`. An entry with `*` as its content format, or `audio/*`, counts as a match for `audio/L16`. L16 entries only at the other rate do not match, since the sender never resamples for a renderer: such a renderer gets WAV if it lists WAV, and is unsupported otherwise, on purpose. A renderer whose sink list matches none of these is unsupported in this version and the host says it does not accept uncompressed audio. *Source:* ConnectionManager:1 §2.5.2 [cm1] (matching with the wildcard); AudioSync design (order).
- **U24** The format that started a session is remembered per renderer `UDN` and tried first next time. *Source:* AudioSync design.
- **U25** The sender starts the stream server for the session (section 5), then calls AVTransport `SetAVTransportURI` with `CurrentURI` set to the stream URL and `CurrentURIMetaData` set to the DIDL-Lite document of U27, then `Play` with `Speed` 1. *Source:* AVTransport:1 §2.4.1 and §2.4.9 [avt1].
- **U26** `SetAVTransportURI` may be sent while the renderer plays something else; the renderer may pass through `TRANSITIONING` before it plays the new URI. The sender does not stop the renderer first. *Source:* AVTransport:1 §2.4.1.3 [avt1].
- **U27** The metadata is a DIDL-Lite document in the namespace `urn:schemas-upnp-org:metadata-1-0/DIDL-Lite/` with the `dc` (`http://purl.org/dc/elements/1.1/`) and `upnp` (`urn:schemas-upnp-org:metadata-1-0/upnp/`) namespaces declared. It holds one `item` with `id` `0`, `parentID` `-1` and `restricted` `1`, a `dc:title` (the stream's title as the host shows it), `upnp:class` `object.item.audioItem.audioBroadcast`, and one `res` whose text is the stream URL and whose `protocolInfo` attribute is `http-get:*:`, the stream's own MIME type with its parameters, `:`, and the fourth field of the sink entry that matched (such as `DLNA.ORG_PN=LPCM`, or `*`). The `res` carries `sampleFrequency` and `nrAudioChannels` and no `duration` or `size`. *Source:* ContentDirectory:1 §2.4.3 Table 3 (required properties `id`, `parentID`, `title`, `class`, `restricted`), §7.1.2 (`audioBroadcast`, a continuous audio stream) and Appendix A (`res` attributes) [cds1]; AVTransport:1 §2.4.1 [avt1] (DIDL-Lite in `CurrentURIMetaData`).
- **U28** The session is playing when `GetTransportInfo` reports `CurrentTransportState` `PLAYING` and the stream server has an open response for the renderer. The sender polls `GetTransportInfo` every 250 ms from `Play` until then, for at most 10 s. *Source:* AVTransport:1 §2.4.4 and §2.4.9.3 [avt1] (`PLAYING`, possibly after `TRANSITIONING`); AudioSync design.

## 5. Serving the audio

- **U29** The stream server is the one the Cast sender already has, used for one renderer: a URL whose host is the literal local address of the interface the renderer was found on, a port the system picks, a path with a random token of at least 128 bits that dies with the session, answers only to the renderer's address (404 for other paths, 403 for other sources), `GET` and `HEAD`, `Range` ignored, each `GET` starting at the live edge with a fresh header, one response at a time, 20 ms blocks never faster than real time, and a 2 s queue that drops the oldest frames on overflow. *Source:* `docs/CAST_SPEC.md` C55 to C61 and C64; AudioSync design (reuse).
- **U30** Three things differ from Cast, and the shared server takes them as options of the session, not as Cast behavior: the `audio/L16` body (U33); `Content-Type` equal to the stream's own MIME type with its parameters, as the `res` of U27 states it; and the framing of U31. No `Access-Control-Allow-Origin` header is needed for a renderer, and sending it does no harm. *Source:* AudioSync design.
- **U31** A request that says HTTP/1.1 gets the chunked transfer coding, as for Cast. A request that says HTTP/1.0 gets no `Transfer-Encoding` and no `Content-Length`: the body runs until the server closes the connection at the end of the session. *Source:* RFC 9112 §6.1 (a server MUST NOT send `Transfer-Encoding` unless the request indicates HTTP/1.1), §6.3 (a response body with no declared length ends when the server closes the connection) and §7.1 [rfc9112]; UPnP Device Architecture 1.1 §2.1 [uda11] (devices must be at least HTTP/1.0 compliant).
- **U32** The renderer fetches at its own pace: HTTP gives no real-time guarantee, and a renderer reads ahead into its own buffer to smooth that out. The server's queue cap (U29) bounds what the host holds; what the renderer holds is not visible to the sender (section 7). *Source:* UPnP AV Architecture:1 §4.2 [av-arch] (read-ahead storage buffer in the renderer for asynchronous-pull transfer).

## 6. Formats

- **U33** `audio/L16`: 16-bit signed two's-complement samples in network byte order (big-endian), two channels interleaved left then right, no header of any kind. The MIME type carries `rate` (44100 or 48000, the stream's rate) and `channels=2`, as `audio/L16;rate=44100;channels=2`. The host's samples, little-endian in memory, are byte-swapped on the server's sending thread, never on an audio callback. *Source:* RFC 2586 [rfc2586] (`rate` required, `channels` optional with default 1, network byte order, lower-numbered channel first); AudioSync design (where the swap happens).
- **U34** LPCM is the DLNA baseline audio format: the guidelines define a set of mandatory media format profiles that every player and renderer must decode, and press coverage of the guidelines names LPCM (or PCM) as the mandatory audio format. A renderer's sink list shows it as `http-get:*:audio/L16;rate=…;channels=…:DLNA.ORG_PN=LPCM` entries, one per rate and channel count. *Source:* IEC 62481-2:2007 introduction [iec-62481-2] (mandatory profiles that renderers have to decode, chosen per region and device category); The Register, 2004 and 2010 [reg-2004], [reg-2010] (LPCM, later "PCM and AAC", as the mandatory audio formats; MP3 and FLAC optional); public user report [ur-rxv773] (an AV receiver's sink list with those four L16 entries).
- **U35** `audio/wav` (and `audio/x-wav` when only that is listed): the Cast sender's live WAV, 16-bit little-endian LPCM in RIFF with the size fields at their largest value. It is the second choice because a sink entry for WAV does not say whether the renderer plays a WAV of unknown length. *Source:* `docs/CAST_SPEC.md` C63; AudioSync design.
- **U36** Lossy formats (MP3 at `audio/mpeg`, AAC) are not streamed in this version. Their trade-offs: they would reach renderers that list no LPCM and cut the stream from about 1.4 Mbit/s to a few hundred kbit/s, which a home network does not need; they add the encoder's look-ahead and frame size to the latency and to the offset's uncertainty; and an encoder must pass AudioSync's rule that bundled dependencies are permissively licensed, which this document does not settle. FLAC is not offered either: the guidelines list it among the optional formats a renderer may refuse. *Source:* ConnectionManager:1 §5.1.1 [cm1] (`http-get:*:audio/mpeg:*` as the example entry); The Register, 2010 [reg-2010] (MP3 and FLAC optional); AudioSync design; UG3 tracks renderers without LPCM.

## 7. Timing and latency

- **U37** What the sender controls: when each byte leaves it, the format (no encoder delay for L16 or WAV), and how much audio waits in its own queue. What it does not control: how much the renderer reads ahead before and while it plays, the renderer's output clock, the delay of whatever the renderer feeds, and the network. AVTransport:1 has no presentation time, no sender clock and no clock exchange; its only position report is `GetPositionInfo`'s `RelTime` and `AbsTime` in hours, minutes, seconds and optional fractions, or `NOT_IMPLEMENTED`. *Source:* AVTransport:1 §2.2.14, §2.2.22, §2.2.23 and §2.4.5 [avt1]; UPnP AV Architecture:1 §4.2 [av-arch].
- **U38** A renderer is therefore a measured-offset output, as `docs/CAST_SPEC.md` C77 says for Cast: the host keeps local speakers and AirPlay receivers in step with it only by delaying them by its measured latency, through the user's per-speaker delay control; the offset is stored per renderer `UDN` and is the starting point of the next session; local outputs never wait for the renderer to start; the host says in its interface that the renderer is kept in step approximately. *Source:* derived from U37; AudioSync design.
- **U39** With no stored offset (none, or 0 ms) the host takes the Cast starting guess for uncompressed audio, 3000 ms, until a measurement replaces it, for the same purpose `docs/CAST_SPEC.md` C77a gives it. *Source:* AudioSync design; no source used here gives a renderer's latency (UG2).
- **U40** The sender counts drift as the Cast sender does (`docs/CAST_SPEC.md` C79): frames dropped on queue overflow, and `TRANSITIONING` after the first `PLAYING`. Above 250 ms of drift since `Play`, the host MAY restart the stream by U45 to bring the latency back to its starting value, and tells the user when it does. *Source:* `docs/CAST_SPEC.md` C75 and C79 (a renderer clock slower or faster than the capture clock fills or drains the queue); derived.
- **U41** While playing the sender polls once per second: `GetTransportInfo`, `GetPositionInfo` and, when the SCPD lists it, `GetVolume`. It logs once per second the audio duration sent since `Play`, frames waiting in its queue, `CurrentTransportState`, `RelTime` and the drift counts. These are diagnostics; the host does not drive the offset from `RelTime`. *Source:* AVTransport:1 §2.3.1 [avt1] (position variables are not evented; a control point may poll `GetPositionInfo` every second while playing); AudioSync design.
- **U42** Eventing (`SUBSCRIBE` to an `eventSubURL`, with changes arriving through the `LastChange` variable) is optional for the sender and not used in this version: it needs a callback HTTP server the renderer can reach, a second listener on the host, while polling needs none. *Source:* UPnP Device Architecture 1.1 §4.1 [uda11]; AVTransport:1 §2.3.1 and RenderingControl:1 §2.3.1 [avt1], [rc1] (all other state variables evented only through `LastChange`); AudioSync design.

## 8. Volume

- **U43** Device volume is RenderingControl `SetVolume` with `InstanceID` 0, `Channel` `Master` and `DesiredVolume` an integer from 0 to the SCPD's `Volume` maximum; `GetVolume` with the same `InstanceID` and `Channel` reads it. 0 is silence and each step of 1 is the device's smallest change. The volume actions are optional in RenderingControl: when the SCPD lists no `SetVolume`, or no `Volume` range, the host shows the renderer's volume control as unavailable and sends nothing. *Source:* RenderingControl:1 §2.2.16, §2.2.19, Table 2-13 and Table 3 [rc1]; RenderingControl:3 action table [rc3] (the volume actions are still optional).
- **U44** Volume maps as for Cast (`docs/CAST_SPEC.md` C104 and C105), with level `v / max` in place of `volume.level`: the host sends `round(m × z × s × max)`, with the master m, zone z and the user's own level s, all 0.0 to 1.0. A level `GetVolume` reports that differs from the last one sent moves the host's control, and is never sent back. While the user drags the slider, at most one `SetVolume` is in flight, the latest value winning. The sender never scales samples for volume. *Source:* `docs/CAST_SPEC.md` C70, C71, C104, C105; AudioSync design.

## 9. Errors and reconnects

- **U45** A restart is: a new stream token, `SetAVTransportURI` with the new URL and the same metadata, then `Play`, as in U25. *Source:* AudioSync design.
- **U46** `SetAVTransportURI` failing with 714 (illegal MIME type) tries the next format of U23 once; with 716 (resource not found), or no fetch of the stream URL within 10 s of `Play`, the attempt ends and the host says the renderer could not reach this computer, naming the firewall as a likely cause, as `docs/CAST_SPEC.md` C56 does. `Play` failing with 701 (transition not available) is retried once after a `GetTransportInfo`. 718 (invalid instance) means the renderer needs `PrepareForConnection`, and the renderer is reported as unsupported (UG4). *Source:* AVTransport:1 §2.4.1.4 and §2.4.9.4 [avt1]; UPnP AV Architecture:1 §4.7 [av-arch]; AudioSync design.
- **U47** While the user still plays: `CurrentTransportState` `STOPPED` or `NO_MEDIA_PRESENT`, `CurrentTransportStatus` `ERROR_OCCURRED`, or the renderer's stream connection closed with no new `GET` within 5 s, leads to one restart (U45). A second such event within 60 s ends the session with its cause. After an error the renderer may be stopped or still playing; which one is up to the device. *Source:* AVTransport:1 §2.2.1, §2.2.2 and §2.4.1.3 [avt1] (`TransportStatus` for asynchronous errors; `STOPPED` when the renderer fails to fetch); AudioSync design.
- **U48** A `TrackURI` from `GetPositionInfo` that is no longer the session's stream URL means another control point replaced the stream: the session ends without a restart and the host shows that the renderer is playing something else. *Source:* AVTransport:1 §2.4.5 [avt1]; AudioSync design.
- **U49** Three polls in a row that fail to connect or time out end the session; the renderer stays listed until U9 drops it. While the user keeps it selected, the sender retries the start after 1 s, doubling the wait up to 30 s, and each attempt takes the address the latest search gave for its `UDN`, with the stream server's allowlist following. *Source:* AudioSync design (as `docs/CAST_SPEC.md` C80 and C111).
- **U50** When the user stops, the sender sends `Stop` (allowed in every state but `NO_MEDIA_PRESENT`), then ends the stream response and closes the stream server. When the host quits, this runs with 3 s in total, then whatever is left is dropped. *Source:* AVTransport:1 §2.4.8 [avt1]; AudioSync design (as `docs/CAST_SPEC.md` C87 and C88).

## 10. Gaps

What a sender needs that no source used here settles. Gaps marked *hardware* need a real renderer.

- **UG1 DLNA HTTP rules** (U29 to U31). The DLNA guidelines define media transfer modes and a live-streaming case [iec-62481-1-1], but their text is not public. Unknown: whether renderers that carry the DLNA logo refuse a stream without DLNA-specific response headers, a chunked body, or a body without `Content-Length`. Settle: *hardware*, the stream server logs each renderer's request header names and HTTP version; a refusal is recorded with model and firmware.
- **UG2 Latency and drift** (U38 to U40). No source gives a renderer's startup latency or read-ahead size. Settle: *hardware*, the click-train measurement of Cast's G7 run on each renderer and format.
- **UG3 Renderers without LPCM** (U23, U36). Unknown: how many renderers list neither L16 nor WAV. Settle: sink lists collected by U22 on every renderer found; lossy encoding is considered only if such renderers turn up.
- **UG4 `PrepareForConnection`** (U19, U46). Unknown: whether any renderer rejects instance 0 without it. Settle: *hardware*, record any 718.
- **UG5 CLOCKSYNC** (U5, U37). AVTransport:3 defines synchronized playback on a shared master clock (`SyncPlay` and a sync offset), advertised through ConnectionManager:3's feature list [avt3], [cm3]. If renderers implemented it, a renderer could leave the measured-offset class. Settle: feature lists read from every AVTransport:3 renderer found; nothing is built before one advertises it.
- **UG6 Several renderers** (U4). Unknown: how far apart two renderers fed the same stream play. Settle: *hardware*, two renderers and one microphone.

## 11. Measured

Read-only black-box run from the Windows PC on 2026-10-30 at night, silent: one SSDP search for `urn:schemas-upnp-org:device:MediaRenderer:1`, sent through Windows' own SSDP service (so no program on the PC opened a listening socket), and nothing else. No action that plays, stops or changes a device was sent.

- The Samsung TV (UT5500 per its AirPlay TXT): untested, TV asleep. It did not answer the search, so its description, SCPDs and `GetProtocolInfo` sink list were not read. It already plays in sync over AirPlay. Its sink list (one silent `GetProtocolInfo`) is the first thing to read when it is awake.
- Two renderers answered, both Windows Media Player renderers provided by Windows: `deviceType` `urn:schemas-upnp-org:device:MediaRenderer:1`, manufacturer Microsoft Corporation, model Windows Media Player, services AVTransport:1, ConnectionManager:1 and RenderingControl:1. They are the reason for U15. Their sink lists were not read; they were outside the brief of this run.

## 12. Go/no-go for code

- Effort: medium. New: SSDP search, description and SCPD parsing, a SOAP client for six actions, the start, poll and restart logic, and a fake renderer for loopback tests. Reused: the Cast stream server (with the three options of U30), the measured-offset handling, the volume mapping and the host's Cast output rows on both hosts. An estimate of the order of the Cast sender's first version minus TLS and its channel protocol, plus Swift wiring on the Mac.
- Risk: renderer variety is the main one (UG1: header and framing quirks that only hardware shows); latency of seconds, as with Cast; no renderer has been measured yet (section 11).
- Overlap with Cast: large. Same class of output, same stream server, same offset and volume model; the new value is only for renderers that have neither AirPlay nor Cast, such as older TVs and AV receivers.
- Recommendation: no-go for code now; keep this specification. Revisit when a renderer without AirPlay or Cast is a real target.
